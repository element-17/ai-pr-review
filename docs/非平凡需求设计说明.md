## 1. F03 启动分析

**目标**：创建任务后异步完成 PR 拉取、文件分析、报告入库，支持排队、取消、重试和失败恢复。

**方案**：
- `TaskCreateService` 同步校验 PR、固定 `head_sha`、写入 `analysis_task(status=1)`，再投递线程池。
- `TaskDispatcher` 定时扫描 status=1，用条件更新 `WHERE status=1` claim 成 status=2，避免重复执行。
- `TaskWorker` 按阶段更新 `stage/progress`，调用 `TaskFileIngestionService` 和分析 pipeline，最终写报告/问题。
- `TaskExecutorConfig` 使用固定 worker 数（默认 2）+ 有界队列；线程名前缀 `analysis-worker-`。
- 任务结束状态：3 完成、4 部分完成、5 失败、6 取消；所有结束都写 `finish_time`。
- 重试只允许 4/5/6，新建任务并记录 `retry_of_task_id`；取消是条件更新，已取消幂等。

**关键边界**：只有 status=1/2 可取消；status=3/4/5/6 取消返回 409；删除只允许本人已结束任务。

## 2. F04 版本一致性

**目标**：报告必须绑定分析时的提交版本，PR 更新后旧报告不能被误认为最新。

**方案**：
- 创建任务时从 GitHub PR 读取 `head.sha`，写入 `analysis_task.head_sha`；`pull_request.head_sha` 单独更新。
- 任务详情 best-effort 刷新 PR 元数据，比较 `task.head_sha` 与 `pull_request.head_sha`，返回 `isExpired`。
- 旧任务、旧报告和旧问题不覆盖；新分析创建新任务。
- 预览的 `reusableTask` 只在同用户、同 PR、同 `headSha`、状态 3/4 时返回。

**交互**：过期提示条 + “重新分析”入口；历史报告仍可查看，但标记为旧版本。

## 3. F05 分层总结 / F06 重点阅读

**目标**：生成 PR 目的、主要变更、影响模块和按文件摘要，并标注重点阅读文件。

**方案**：
- `DeepSeekAnalysisPipeline` 阶段 1 构造 PR/commit/文件元数据上下文，调用 `submit_summary`。
- `SummaryDraft` 保存 `purpose/changes/impacts/files[]`；`files[]` 包含 `path/summary/priorityReason`。
- `AnalysisReport` 持久化三段总结；`task_file.summary` 和 `task_file.priority_reason` 持久化文件级说明。
- 任务详情返回 `priorityFiles`（最多 20 个，按问题数量/优先级排序）和文件列表 summary。
- 阶段 1 失败是致命失败，任务进入 status=5，不生成假报告。

**控制**：模型只能引用文件清单中的路径；未知路径的摘要被忽略；总结为空时按格式错误处理。

## 4. F08 候选问题识别

**目标**：按 7 类风险识别候选问题，输出结构化字段，不把模型自由文本直接入库。

**方案**：
- 阶段 2 每批 3–5 个文件，构造 patch、文件内容摘要、检查类别、报告语言。
- `submit_issues` schema 要求 `title/category/severity/confidence/triggerCondition/impact/suggestion`；`filePath/startLine/endLine/evidence` 可选。
- `IssueDraft`/`IssueDraftList` 解析工具参数；类别 1–7、严重度 1–4、置信度 0–100。
- `IssueValidationService` 做文件归属、行号、范围和证据校验后写 `review_issue`。
- 批次失败只影响该批文件；其他批次和报告保留。

## 5. F10 上下文分析

**目标**：在 GitHub 只读范围内补充函数、import、调用方和测试上下文，控制 token 和隐私。

**方案**：
- `ContextBuilder` 通过 GitHub Contents API 读取固定 `head_sha` 的文件，单文件上限 20KB，路径拒绝绝对路径和 `..`。
- `TypeScriptContextExtractor`/`PythonContextExtractor` 提取变更行所在函数、import；失败回退到变更行附近窗口。
- Agent 工具：`read_file`、`find_callers`、`read_tests`；只读、限文件数、无 shell/任意网络。
- `ContextFileCache` 使用 `ConcurrentHashMap`，任务内共享，不把代码全文写 Redis/DB。
- PR 内容和代码视为不可信输入；系统提示要求忽略代码注释中的指令。

## 6. F11 核验与降噪

**目标**：拒绝无法定位/无证据/非法枚举的模型输出，减少编造和重复。

**方案**：
- `PatchLineIndex` 解析 hunk，记录新文件侧新增行和 hunk 覆盖行。
- 文件必须属于任务；有文件的 issue 必须有起始行；行号不落在新增行时降置信度，完全不在 hunk 时进一步降低。
- 纯删除/没有新文件侧行号时降级为报告级（fileId/行号为空）。
- 证据为空时置信度上限 60；重复键 `fileId + category + 规范化 title` 只保留一条。
- 校验丢弃数量>0 时批次标记部分完成；批次模型异常/格式异常不覆盖已入库结果。

## 7. F12 建议生成

**目标**：每条问题给出可执行建议，并关联触发条件、影响和证据。

**方案**：
- `submit_issues` 要求 `suggestion` 非空；prompt 要求写“核查/修复/补测试”动作，不声称已确认缺陷。
- `review_issue.ai_suggestion` 保存模型原文，`suggestion` 保存当前（可编辑）建议。
- PATCH 建议非空、最长 5000；撤销恢复 `ai_suggestion`。
- 置信度、严重度和证据在详情中分开显示，前端不把低置信度包装成确定缺陷。

## 8. F17 失败恢复

**目标**：失败原因可定位、可重试，部分结果不被清空。

**方案**：
- `TaskWorker` 将 `ModelException`、`AnalysisPipelineException`、`GitHubApiException` 和其他异常映射到 `errorCode`：
  - 1 PR 无效、2 GitHub 限流、3 权限、4 GitHub 失败/超时、5 Diff 过大、6 模型超时、7 模型格式/部分丢弃、8 内部错误。
- 模型超时/部分批次失败 → status=5 或 4，保留已有报告/问题；启动时 status=2 → 5/8。
- 手动重试只允许 4/5/6，创建新任务并保留旧任务。
- 前端根据 `canRetry/errorCode` 展示原因与重试入口。

## 9. F18 账户与数据保护

**目标**：登录、退出、刷新和任务归属安全，游客链接可分享但不可越权。

**方案**：
- 密码 BCrypt；Sa-Token opaque access-token 30 分钟；refresh-token 存 Redis 7 天，刷新旋转并撤销旧 token。
- 登录失败按用户名计数（5 次/15 分钟），不按 IP；退出注销当前 access-token 并删除该用户 refresh-token。
- `TaskAccessService` 统一校验任务归属：登录本人、或匹配且未过期 guestToken；无效 Authorization 在任务子资源不能静默降级为游客（创建/预览除外）。
- 游客 token 随机 64 位 hex，任务级绑定，默认 7 天；游客不能列表、删除、设置、管理员接口。
- 用户设置只返回主题/语言/检查项/上限，不返回模型 Key；日志格式化脱敏 Authorization/token/password/api-key。

## 10. F20-BE 可交互 Diff

**目标**：把 patch 变成前端可直接渲染的结构化行，并把问题映射到新文件侧行号。

**方案**：
- `PatchDiffParser` 解析 `@@`、add/delete/context/meta，维护旧/新行号。
- `TaskFileDiffVO` 继承文件详情，增加 `rows`、`addedLines`、`hunkLines`、`patchAvailable`。
- `DiffRowVO`：`type/oldLine/newLine/content/issueIds/highestSeverity`。
- `TaskFileServiceImpl.getDiff` 复用文件详情权限和问题列表，按 `newLine` 落入问题区间添加 issue ID。
- 接口 `GET /api/tasks/{taskId}/files/{fileId}/diff`；报告级问题不映射到行，仍从 `issues` 读取。
- 原 patch 详情接口保留，前端可按需选择。

## 11. F22-BE 版本对比

**目标**：对比同一 PR 两个分析版本的问题和总结变化。

**方案**：
- `TaskCompareService` 校验本人、同一 PR、状态 3/4、至少一个报告或问题。
- 匹配键：文件路径（含 oldPath/newPath 别名）+ 类别 + 规范化标题。
- 精确匹配 → remaining；目标有/基线无 → added；基线有/目标无 → resolved。
- 行号变化标记 `lineShifted`；同类别/路径交集/行号重叠但标题不同 → remaining + `matchConfidence=low`。
- 返回三段 summary 的 base/target/changed、任务统计和匹配说明；不实现增量计算，不新增表。

## 12. D01 平台实现与模块边界

**目标**：控制器、业务服务、任务引擎、AI 分析和外部集成职责清晰。

**方案**：
- 单 Maven 模块，按职责分包，对齐 `sky-take-out`：
  - `controller`、`service/service.impl`、`task`、`analysis`、`integration`、`mapper/entity/dto/vo`。
  - `exception`、`handler`、`properties`、`utils`、`logging`、`filter`、`constant/context/result`。
- Controller 不写业务；Service 负责权限/事务；`analysis` 负责模型编排；`integration` 只做外部协议。
- 自定义异常集中 `exception`，全局处理在 `handler`；工具不混入 service。

## 13. D02 模型选择

**目标**：至少比较两种模型/配置的结构化稳定性、延迟和 token，给出默认选择。

**方案**：
- `backend/scripts/model-comparison.mjs` 读取本地 gitignored 配置，不输出 Key。
- 5 个受控变更：README 拼写、JS 空值、Python 异常、TS 跨函数、无缺陷文档。
- 统一 system prompt、`submit_issues` tool schema、temperature 0.1、max_tokens 2048。
- 结果：两者 5/5 结构化、5/5 schema、5/5 核心缺陷；Flash 30.2s/7,229 tokens，Pro 53.2s/7,916 tokens。
- 默认 `deepseek/deepseek-v4.1-flash`；Pro 作为复杂/高价值 PR 可选；详见 `docs/模型对比与选型.md`。

## 14. D03 上下文控制

**目标**：大 PR 不无限读取/无限调用模型，控制上下文、并发和成本。

**方案**：
- 文件数、单文件 patch、单文件内容、Diff 行数均有上限；超限写 `task_file.skip_reason` 并标记跳过。
- 每批 3–5 文件；`pr.ai.batch-concurrency`（1–4，默认 2）控制批内并发；`ExecutorCompletionService` 汇总结果。
- 单批失败隔离；问题入库串行化避免重复竞争；批次完成推进 50–89 进度。
- 取消在批边界检查，取消后中断剩余批次；批线程继承 `task-{id}` traceId。
- 实测 187 文件：46 批/并发 2，analyzed=184、skipped=3、60.1s（串行 137.6s）。

## 15. D04 性能与可用性

**目标**：异步、可取消、可轮询、可恢复，外部调用有超时和重试边界。

**方案**：
- 固定 worker + 有界队列；任务状态/阶段持久化，刷新后从详情恢复。
- 轮询 `/progress`，前端 2 秒一次；终态 3/4/5/6 停止。
- GitHub 客户端连接/读取超时、429/5xx 有限退避；模型客户端连接/读取超时。
- 启动恢复：status=2 标记失败 5/8；status=1 重新投递。
- 阶段/渠道耗时写日志：文件拉取、AI 分析、模型 token/耗时、GitHub 慢请求。
- 大 PR 通过 D03 的有界并发控制吞吐和资源。

## 16. D05 质量验证

**目标**：20+ 案例、可复现指标、误报漏报分析。

**方案**：
- `docs/测试用例与指标.md` 记录 20 个用例、真实模型指标、误报漏报和限制。
- 真实模型：README PR status=3、20.8s、3 次调用、4,504 tokens；2 处拼写缺陷检出。
- 严格问题有效率 50%（1 拼写 + 1 主观建议）；行号定位 1/1。
- 大 Diff、模型超时、启动恢复、非法输出部分完成均有实测。
- 本轮补充 40 项 API/状态回归（`docs/全量业务回归与状态验证.md`）。

## 17. D06 安全与交付

**目标**：可交付的容器/反向代理材料，密钥不进入仓库和镜像。

**方案**：
- `backend/Dockerfile` 多阶段 JDK 17 构建，运行非 root；`.dockerignore` 排除本地配置/日志/target。
- `deploy/docker-compose.yml`：MySQL 8.4、Redis 7.4、Backend、Nginx；MySQL/Redis 不映射宿主端口。
- Nginx 反代 `/api/`、SPA 回退、安全响应头、`X-Request-Id` 透传；前端产物由部署方复制。
- `.env.example` 只放占位符；`.env`、`application-dev.yml` 已忽略。
- 部署/安全清单见 `docs/部署与安全检查.md`；当前机器无 Docker，容器构建和 `nginx -t` 待目标机复验。
