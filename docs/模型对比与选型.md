# D02 模型对比与选型

> 执行时间：2026-10-22
> 对比模型：`deepseek/deepseek-v4.1-flash`、`deepseek/deepseek-v4-pro`
> 调用方式：OpenAI 兼容 `/chat/completions`，同一 system prompt、`submit_issues` tool schema、`temperature=0.1`、`max_tokens=2048`、`thinking=disabled`
> 可复现脚本：`backend/scripts/model-comparison.mjs`（读取本地 gitignored 配置或环境变量，不输出 Key）

## 1. 方法

使用 5 个受控变更案例，每个模型对每个案例独立调用一次，要求模型只通过 `submit_issues` 返回结构化候选问题：

1. README 两处拼写错误（`Softwarw`、`fir`）
2. JavaScript 用户对象空值边界
3. Python 字符串转整数异常处理
4. TypeScript 跨函数传入 `undefined as any`
5. 纯文档、无代码缺陷

统一记录：是否调用工具、参数是否通过 schema 校验、问题数量、问题内容、延迟和 token。问题质量按“是否覆盖预期核心缺陷”和“是否产生无证据/主观问题”人工复核。

## 2. 结构化稳定性与耗时

| 指标 | v4.1 Flash | v4 Pro |
| --- | --- | --- |
| 案例数 | 5 | 5 |
| 成功返回 `submit_issues` | 5/5 | 5/5 |
| schema 校验通过 | 5/5 | 5/5 |
| 总问题数 | 10 | 6 |
| 总耗时 | 30,232 ms | 53,200 ms |
| 平均耗时 | 6,046 ms | 10,640 ms |
| 总 token | 7,229 | 7,916 |
| 平均 token/案例 | 1,446 | 1,583 |
| 预期核心缺陷覆盖 | 5/5 | 5/5 |

Flash 平均延迟比 Pro 低约 **43%**，token 少约 **8.7%**。两者在本次样本中都没有出现“只返回自然语言、不调用工具”的结构化失败。

## 3. 分案例结果

| 案例 | 预期核心问题 | v4.1 Flash | v4 Pro |
| --- | --- | --- | --- |
| README 拼写 | `Softwarw` / `fir` | 1 条，覆盖两处拼写，low/92 | 1 条，覆盖拼写，low/95 |
| JS 空值边界 | `user`/`user.name` 未校验 | 2 条：空值 TypeError（high/85）+ 全空白昵称（low/55） | 1 条：空值校验（medium/85） |
| Python 异常 | `None`/非字符串、`int()` 失败 | 4 条：类型、ValueError、缺测试、负号语义 | 2 条：类型、ValueError |
| TS 跨文件 | `undefined as any` 运行时错误 | 3 条：undefined、normalize 入参、缺测试 | 1 条：undefined 运行时错误 |
| 纯文档无缺陷 | 不产生 high/critical | 0 条 | 1 条 low：“Usage 缺少命令名/示例” |

### 质量口径

- 预期核心缺陷共 5 个，两个模型均检出 5/5。
- 严格问题有效率（核心问题 / 全部问题）：
  - Flash：5/10 = **50%**；额外问题主要是低严重度的测试/语义建议，部分有价值但偏多。
  - Pro：5/6 = **83.3%**；额外 1 条为纯文档主观建议（误报）。
- 宽松口径下，Flash 的低严重度建议多数可作为人工提示；Pro 输出更克制，但仍有 1 条无代码证据的文档建议。

## 4. 结论与选择

**默认选择 `deepseek/deepseek-v4.1-flash`。**

理由：

1. 结构化输出稳定性与 Pro 相同（5/5 工具调用、5/5 schema 校验）。
2. 预期核心缺陷全部检出，问题数量更多但以低严重度提示为主，可通过现有置信度/证据校验和人工反馈降噪。
3. 平均延迟低约 43%，token 少约 8.7%，更适合异步分析主链路。
4. `v4-pro` 输出更简洁，严格有效率更高，但延迟和 token 成本更高；保留为复杂/高价值 PR 的可选配置。

运行时仍通过 `pr.ai.deepseek.model` 一行切换；不引入第二套客户端或数据库字段。D02 的“模型输出校验与降级”已由 `IssueValidationService`、`IssueValidationResult` 和 F11/F12 的行号/证据/去重逻辑覆盖。

## 5. 局限

- 每个案例只执行一次，未做多次采样；模型波动未完全量化。
- 使用单轮工具调用，不复现完整 agent 工具循环和多批上下文。
- 5 个受控案例覆盖空值、异常、跨函数和文档，但没有大型真实 PR 的复杂业务缺陷。
- 实际单价依赖 provider 计费，本报告只用 token 作为成本代理，不虚构金额。
- 下一步可对 10–20 个真实 PR 做双模型采样，并记录人工采纳率，再决定是否把 Pro 作为高风险 PR 的默认模型。
