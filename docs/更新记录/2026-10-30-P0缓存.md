# P0 缓存更新记录

## 一句话摘要

本次为后端增加用户设置、终态任务详情/报告/文件列表、结构化 Diff 四类 Redis 缓存，通过物理 TTL 抖动、空值缓存、逻辑过期异步刷新分别应对雪崩、穿透、击穿；所有任务缓存均在权限校验之后读取。

## 背景与目标

- 目标：降低高频读接口对 MySQL 的压力，同时保证权限、终态数据和反馈失效的一致性。
- 范围：仅 `backend/`，不修改正式前端，不新增 Maven 依赖，不变更数据库 schema 文件。
- 非目标：加分项、全量业务数据缓存、运行中任务的实时缓存。

## 缓存设计

| 数据 | Key | 物理 TTL | 逻辑 TTL | 失效时机 |
|---|---|---|---|---|
| 用户设置 | `user:setting:{userId}` | 10 分钟 + 0~120 秒抖动 | 无（注解缓存） | PATCH 设置、初始化默认设置 |
| 任务创建配置 | `user:setting:config:{userId}` | 10 分钟 + 0~120 秒抖动 | 无（注解缓存） | PATCH 设置、初始化默认设置 |
| 任务详情 | `task:detail:{taskId}` | 30 分钟 + 0~300 秒抖动 | 5 分钟 + 0~20% 抖动 | 反馈 update/undo、删除任务 |
| 任务报告 | `task:report:{taskId}` | 30 分钟 + 0~300 秒抖动 | 5 分钟 + 0~20% 抖动 | 反馈 update/undo、删除任务 |
| 文件列表 | `task:files:{taskId}:{queryKey}` | 30 分钟 + 0~300 秒抖动 | 5 分钟 + 0~20% 抖动 | 删除任务（按前缀） |
| 文件 Diff | `task:file:diff:{taskId}:{fileId}` | 30 分钟 + 0~300 秒抖动 | 30 分钟 + 0~20% 抖动 | 反馈 update/undo、删除任务（按前缀） |

说明：

- `queryKey` 由页码、每页数量、status、changeType、priorityOnly、keyword、sort 拼接，避免把 DTO 对象地址作为 key。
- 只缓存终态任务（status=3/4/5/6）；排队中、分析中任务直接查询数据库，避免进度和状态陈旧。
- 文件详情未单独缓存：P0 的 key 表只覆盖文件列表和 Diff；文件详情包含 `feedbackStatus`，单独缓存会引入反馈后的旧值窗口。`getDetail` 仅拆出 `buildFileDetail` 供 Diff 复用。
- 报告为空时缓存 `CacheEnvelope(data=null)`，接口业务码仍为 404，用于防止反复查询不存在的报告。

## 三个问题怎么解决

- 缓存雪崩：每个用户的设置缓存、每个任务缓存 entry 的物理 TTL 都增加随机抖动；逻辑过期时间额外增加 0~20% 抖动，避免同一批 key 同时失效。
- 缓存穿透：允许缓存空结果。`RedisCacheConfiguration` 未调用 `disableCachingNullValues()`；逻辑缓存使用 `CacheEnvelope` 包住数据，`data` 允许为 null；终态失败/取消任务的报告不存在时缓存 null。
- 缓存击穿：任务详情/报告/文件列表/Diff 使用逻辑过期。逻辑过期后先返回旧值，再用 `SETNX cache:lock:{cacheName}:{key}`（30 秒 TTL）抢锁，抢到锁的实例提交到 `cacheRefreshExecutor` 异步刷新；未抢到锁直接返回旧值。缓存未命中时抢锁同步加载，未抢到锁短暂重试 3 次（每次 50ms），仍无结果再同步加载兜底。

## 一致性与权限

- 写路径采用 Cache-Aside：先写数据库，再删除缓存；读路径回填。用户设置通过 `@CacheEvict` 删除；反馈和删除任务通过 `LogicalCacheService.evict` / `evictByPrefix` 删除。
- 所有任务缓存都在 `taskAccessService.requireAccessibleTask` / `requireOwnedTask` 之后读取，缓存命中不能绕过越权校验。
- 缓存 loader 只做纯数据库查询，不依赖 Sa-Token 请求上下文。`TaskDetailVO.canDelete` 依赖当前登录身份，已从 `buildDetail` 移到 `getDetail` 的请求线程内，在缓存读取之后按请求设置；异步刷新线程不再访问 Sa-Token。
- 反馈 update/undo 失效：`task:detail:{taskId}`、`task:report:{taskId}`、对应文件的 `task:file:diff:{taskId}:{fileId}`；文件列表不含反馈字段，不失效。
- 删除任务失效：`task:detail:{taskId}`、`task:report:{taskId}` 精确删除，`task:files:{taskId}:*`、`task:file:diff:{taskId}:*` 使用 SCAN 按前缀删除，不使用 `KEYS`。
- 取消任务不失效：运行中任务本来不写缓存。

## 风险与后续

- 多实例：逻辑刷新锁使用 Redis `SETNX`，锁 TTL 30 秒且没有续期；若 loader 执行超过 30 秒，可能出现重复刷新。当前 loader 为本地数据库查询，风险可控。
- 旧值窗口：详情/报告/文件列表最长约 5 分钟 + 20% 抖动，Diff 最长约 30 分钟 + 20% 抖动；反馈和删除会主动失效，PR head_sha 刷新不会主动失效，详情中的过期状态可能短暂滞后。
- 详情刷新链路保留 `pullRequestRefreshService.refreshIfStale`：异步刷新时若 60 秒 PR 刷新缓存不存在，可能触发一次 GitHub 调用；失败会回退缓存值，不阻塞请求线程。
- 文件列表目前不含反馈字段，因此反馈不失效文件列表；若后续列表加入反馈统计，需要把 `TASK_FILES` 加入反馈失效矩阵。
- `GenericJackson2JsonRedisSerializer` 在 Spring Data Redis 4.0 中已标记为过时（仍可用）。后续可迁移到 Jackson 3 的 `GenericJacksonJsonRedisSerializer`，本次按已批准方案保留 Jackson 2 + `JavaTimeModule`。
- 报告 404 沿用项目既有的 HTTP 200 + 业务码约定；如需改为真实 HTTP 404，需要统一调整全局异常处理，影响面较大，未纳入本次 P0。
- 未做：加分项 X01–X08、正式前端改动、数据库 schema 文件变更、容器部署复验。

## 汇报口径

- 本次缓存不是“全量加缓存”，而是按读多写少、终态数据优先选择：用户设置、终态任务详情/报告/文件列表、结构化 Diff。
- 三类经典问题分别用物理 TTL 抖动、空值缓存、逻辑过期 + Redis 锁 + 异步刷新处理；逻辑过期时先返回旧值，保证请求不被阻塞。
- 权限校验在缓存之前，缓存 loader 只做纯 DB 查询，不依赖 Sa-Token 上下文；`canDelete` 这类身份相关字段在缓存读取后按请求计算，避免越权和串值。
- 写操作采用“写数据库后删缓存”，反馈和删除都有明确失效点；删除任务按前缀 SCAN 清理文件列表和 Diff。
- 实测验证了 key、TTL、空值缓存、反馈/删除失效和逻辑过期异步刷新，测试 16 个用例通过，夹具已清理。
