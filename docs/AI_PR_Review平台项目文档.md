# AI PR Review 助手平台项目需求文档

> 说明：本文是项目目标与需求基线，不是当前实现状态的唯一来源。后端实现进度、接口和测试见 [docs/README](README.md)、[接口文档](接口文档.md) 和 [测试用例与指标](测试用例与指标.md)。

项目定位：面向开发者的 GitHub Pull Request 智能评审 Web 平台。用户通过浏览器提交 PR，平台获取代码变更、组织上下文、生成 AI 分析，并在评审工作台中完成核对与反馈。平台提供浅色、深色、跟随系统的主题切换，以及简体中文与英文界面。本文定义功能、开发要求与验收方式，供团队继续开展需求分析和任务拆分。

## 一 项目目标与使用场景

在实际代码评审中，评审者通常需要先理解 PR 的修改意图，再逐文件阅读 Diff，查找相关函数、调用方和测试，最后判断是否存在可复现的风险。大 PR、跨文件修改与缺乏上下文的代码片段会显著增加阅读成本；未经核验的大量 AI 提示也容易制造误报。

开发者在网页中输入 GitHub PR 链接，平台获取变更并生成可追溯的分析结果。平台负责整理信息和提出候选问题，最终 Review 结论由开发者确认。首期以公开仓库 PR 的手动分析为主；私有仓库接入与自动触发作为扩展功能。

## 二 平台使用者与操作流程

平台只有一类主要使用者：需要分析 PR 的开发者。他可能是 PR 作者，也可能是评审者，无需为这两种身份设计不同的角色权限。游客可分析公开 PR；登录用户可保存和查看自己的历史任务与反馈。

典型操作：进入平台并粘贴 PR 链接，查看任务进度；在评审工作台阅读摘要、Diff 和风险证据；人工确认、编辑或忽略建议；导出 Review 报告。登录用户还可从历史任务页重新打开分析结果。

## 三 功能需求

### 3.1 PR 接入与任务管理

- **F01 输入 PR：** 在首页输入 GitHub PR URL，校验格式、仓库与 PR 是否存在，展示仓库、编号、标题、作者、分支、状态和提交版本；无效链接与无权限情况给出明确提示。

- **F02 获取变更：** 拉取 PR 描述、文件清单、补丁片段与必要的提交信息；显示每个文件的新增/删除行数、变更类型和语言。对重命名、删除、二进制文件与过大的 Diff 明确标识。

- **F03 启动分析：** 在网页发起、取消或重试任务，展示排队、获取代码、分析中、已完成、部分完成和失败等状态与阶段进度；相同提交版本可提示复用已有结果。

- **F04 版本一致性：** 每次任务关联 PR 的 head commit SHA。PR 新增提交后，旧报告显示“已过期”，用户可发起新任务；旧结果仍可查看，但不应误标为最新结果。

### 3.2 变更理解与总结

- **F05 分层总结：** 在评审工作台生成整篇 PR 的修改目的、主要变更、可能影响的模块，以及按文件或逻辑模块划分的简述。总结应能区分新增功能、缺陷修复、重构和测试修改，避免只重复文件名与代码表面变化。

- **F06 重点阅读：** 标出应优先人工检查的文件或变更块，并解释原因，例如鉴权、数据迁移、接口兼容、异常处理、并发或配置变更。支持从总结跳转到对应 Diff。

- **F07 覆盖说明：** 报告展示纳入分析的文件数量、跳过的文件及跳过原因；不能把“未发现问题”等同于“代码已被证明正确”。

### 3.3 风险识别与证据展示

- **F08 候选问题识别：** 至少覆盖逻辑错误、空值与边界条件、异常处理、权限或敏感信息、接口或数据兼容、缺失的关键测试等类别。项目可按所选语言重点实现部分规则，并说明范围。

- **F09 问题结构：** 每条风险包含标题、类别、严重度、判断置信度、文件路径与变更行号、触发条件、潜在影响、证据片段和建议的验证方法；证据不足时标记“待人工确认”。

- **F10 上下文分析：** 对变更函数补充必要的定义、类型、直接调用方和相关测试。至少支持一种语言（TypeScript 或 Python）的函数级上下文获取，并能展示一个跨文件关联分析案例。

- **F11 核验与降噪：** 检查问题定位是否落在当前 PR 的有效变更行，合并同根因的重复提示；对纯风格偏好不生成高风险告警。无法确认时降低置信度，禁止编造不存在的文件、符号或调用关系。

### 3.4 Review 建议与人工反馈

- **F12 建议生成：** 针对可疑问题给出简短、可执行的 Review 建议，包括要核查的条件、可能的修复方向或补充测试。建议与风险证据关联，不直接宣称已经验证缺陷。

- **F13 交互评审：** 点击风险项在网页 Diff 中定位对应代码，并可跳转 GitHub 原始页面；支持按严重度、类别、文件和处理状态筛选。开发者可采纳、编辑、标记误报、已解决或待确认，并记录理由。

- **F14 结果导出：** 将 PR 信息、提交版本、总结、风险清单、人工处理结论与未覆盖范围导出为 Markdown 报告。首期不自动向 GitHub 发布行内评论。

- **F15 历史记录：** 登录用户可在任务页查看自己提交的 PR 分析、提交版本、状态和时间，按仓库、PR 编号和时间筛选并分页；游客任务可通过结果链接在有效期内查看，具体保存期限由团队说明。

### 3.5 配置与异常处理

- **F16 平台设置：** 登录用户可配置重点检查类别、忽略目录、分析规模上限、主题和界面语言。模型密钥由服务端配置，不在网页中展示；报告记录本次分析使用的非敏感配置。

- **F17 失败恢复：** GitHub 接口限流、仓库无权限、模型超时、响应格式错误、Diff 过大时，展示具体原因与重试入口。部分文件完成时保留已得结果并标记“部分完成”。

- **F18 账户与数据保护：** 公开 PR 支持游客分析；平台至少提供一种登录方式（邮箱密码或 GitHub 授权）及退出功能。登录用户只能查看和操作自己的任务与反馈；密码或令牌须安全保存，服务端密钥不得写入前端代码或日志。调用外部模型前应提示代码会发送至所配置的服务。

### 3.6 网页评审工作台

- **F19 工作台总览：** 提供独立的 PR 评审页面，展示基本信息、变更统计、分析进度、风险分布、重点文件和未覆盖范围；点击模块可进入对应详情。

- **F20 可交互 Diff：** 按文件浏览变更，支持并排或统一视图、语法高亮、变更行标识和文件切换；风险标记与代码行联动，点击后展开证据与建议。大文件采用按需渲染或分段加载，保持页面流畅。

- **F21 问题管理界面：** 以列表与详情视图展示风险，可组合筛选、排序、关键词搜索，并显示处理进度。支持逐条编辑建议、提交反馈、撤销误操作和跳转下一条未处理问题。

- **F22 版本对比界面：** 对同一 PR 的两个分析版本展示新增、仍存在、已消失的问题和总结变化；提示可能由行号变化造成的匹配不确定性。版本对比只是结果展示，不要求基础版实现增量计算。

- **F23 状态与设置界面：** 为加载、空结果、部分完成、失败、过期和取消状态分别设计界面；提供检查偏好、忽略目录、主题语言与数据发送提示，避免只显示通用错误弹窗。

- **F24 交互体验：** 工作台适应桌面和常见平板宽度，支持键盘操作与清晰的焦点状态；从风险列表返回 Diff 时保留文件、滚动位置和筛选条件。

### 3.7 主题与双语言切换

- **F25 主题切换：** 提供浅色、深色、跟随系统三种主题选项。切换后总览、Diff、风险标记、图表和设置页同步更新；选择应保存并在下次访问时恢复。跟随模式响应操作系统主题变化，代码高亮与告警颜色在两种主题下均须可辨。

- **F26 双语言界面：** 完整支持简体中文和英文，设置页可即时切换。导航、按钮、筛选项、状态、错误提示、空结果、帮助说明和日期数字格式应随界面语言变化；选择应保存并在下次访问时恢复。

- **F27 报告语言：** 分析前可选择 AI 总结与 Review 建议使用中文或英文，默认跟随界面语言；导出报告沿用本次分析语言。切换界面语言不自动改写已生成的 AI 内容，历史报告应显示其生成语言，用户可重新分析以获取另一语言版本。

## 四 关键业务规则与流程

- **B01 评审版本：** 任务的输入由仓库、PR 编号和 head commit SHA 确定；同一报告的总结、问题和行号必须来自同一版本。

- **B02 风险分级：** 严重度描述潜在影响，置信度描述证据充分程度，两者分开展示。高严重度但低置信度的问题应提醒人工优先核查。

- **B03 有效定位：** Review 建议必须关联可查看的文件与行号；无法定位到变更行的跨文件推断，可以作为报告级提示，不伪装为行内评论。

- **B04 部分结果：** 部分完成或跳过文件时，报告必须附分析范围与原因，任务不能直接显示为完整成功。

建议流程：提交 PR → 拉取元数据与 Diff → 识别变更范围并补充上下文 → 生成总结与候选问题 → 校验位置及证据、去重 → 展示报告 → 人工反馈 → PR 更新后重新分析。

## 五 开发要求

- **D01 平台实现：** 交付可运行的 Web 前端、Java Spring Boot 后端与 AI 分析模块。前端负责 PR 提交、任务进度、Diff 和反馈；后端负责 GitHub 数据获取、任务调度、上下文组织、模型调用、结果持久化与权限校验，并说明模块边界。

- **D02 模型选择：** 至少比较两种可用模型或两种配置的代码理解效果、结构化输出稳定性、响应时间与调用成本，说明最终选择；不要求训练模型。模型输出需经过字段和行号校验后入库。

- **D03 上下文控制：** 制定上下文获取范围与截断策略，优先读取变更函数、依赖定义和相关测试；说明大 PR 的分块、并发或增量处理方式。后端可通过 GitHub API 或受控的临时检出获取仓库代码，不得假设浏览器能直接读取用户本地仓库；PR 文本与仓库代码按不可信输入处理。

- **D04 性能与可用性：** 分析任务异步执行且可取消，页面通过轮询或服务端推送展示进度，刷新后能重新进入任务。为 GitHub 请求和模型调用设置超时、限流处理与重试边界，记录耗时与失败阶段。

- **D05 质量验证：** 建立至少 20 个有明确预期的测试 PR 或变更案例，覆盖普通修改、跨文件依赖、已知缺陷、无缺陷、大 Diff 与异常场景。记录问题有效率、已知缺陷检出率、定位准确率和耗时，分析典型误报、漏报。

- **D06 安全与交付：** 不得在代码库提交密钥，日志不得包含访问令牌或完整私有代码。提供前后端启动与部署说明、数据库初始化脚本、配置示例、接口文档、演示用 PR、测试结果和系统设计说明。

- **D07 前端实现：** Web 平台至少包含首页、任务列表、PR 总览、文件 Diff、问题详情与处理、版本对比、设置七类界面。采用可复用组件与界面状态、统一的主题变量和中英文资源文件，提供界面原型和主要交互流程说明。

## 六 验收标准

- **A01 端到端演示：** 在浏览器中使用真实公开 GitHub PR 完成“输入链接—获取变更—生成总结与风险—定位 Diff—人工处理—导出报告”的完整流程。

- **A02 分析可信度：** 至少演示一个跨文件问题；每条展示的风险可追溯到正确的文件与版本，具有触发条件和证据，误报可由评审者反馈。

- **A03 异常与更新：** 演示无效链接、接口失败或模型超时的提示和恢复方式，以及 PR 新提交后旧报告过期的处理。

- **A04 评估材料：** 提交测试案例及汇总指标，解释模型选择、上下文获取、误报与漏报控制、响应速度之间的取舍。

- **A05 界面验收：** 现场演示从总览筛选问题、在 Diff 中定位证据、编辑并反馈建议、查看新旧版本差异，以及加载失败和部分结果状态；在桌面和常见平板宽度下保持可读和可操作。

- **A06 主题与语言验收：** 依次切换浅色、深色、跟随系统主题，并更改操作系统主题，检查各页面同步变化；切换中文与英文后检查正常、空结果及错误状态。刷新页面验证偏好保留，并确认旧报告不会因界面语言切换而被悄悄改写。

## 七 加分项与扩展方向

以下功能属于可选加分项，不替代第三至第六部分的基础要求。团队可根据时间选择其中几项深入实现；演示时应给出真实 PR、操作过程或对比数据，说明扩展确实产生了效果。

- **X01 增量评审：** PR 新增提交后，仅重新获取和分析受影响的文件或代码块，保留未变化的有效结果。演示同一 PR 两个提交版本的差异，并给出相对完整重跑的耗时与模型用量对比。

- **X02 仓库级上下文检索：** 在函数级上下文之外，通过符号索引或检索查找调用链、接口定义、配置和测试，发现仅看 Diff 难以识别的跨文件问题。演示至少一个关联多个文件的案例，并显示证据来源。

- **X03 人工确认后发布评论：** 开发者在平台中编辑、确认建议后，才将其发布为 GitHub PR 行内评论；需处理行号映射、重复发布和 PR 更新后的失效位置。演示发布前预览与发布后的 GitHub 页面结果。

- **X04 私有仓库支持：** 通过 GitHub 授权访问私有 PR，限制授权范围，安全保存和撤销凭证；清理任务日志中的敏感信息。演示授权、分析与撤销后的访问变化，不在演示材料中泄露私有代码。

- **X05 测试辅助：** 根据风险问题生成针对触发条件和边界情况的测试思路，进一步可提供可复制或下载的测试代码草稿；演示测试如何复现或排除某个候选问题。

- **X06 反馈驱动的质量改进：** 汇总采纳、误报和漏报反馈，按问题类别统计效果，并用相同测试集比较优化前后的问题有效率、检出率和耗时。可调整提示词、规则或模型配置，但须展示可复现的对比结果。

- **X07 自动触发与通知：** 通过 GitHub App 或 Webhook 在 PR 创建、更新时触发分析，在平台内提示新报告。应校验事件来源、避免同一提交重复执行，并演示一次完整的自动触发流程。

- **X08 多语言与可配置规则：** 在首期支持的语言之外增加另一门语言的符号级分析，或支持可共享的团队规则，例如重点检查鉴权与接口兼容。演示规则启用前后的结果差异，并说明适用范围与误报风险。
