# 云效平台管理快速上手

> 适用范围：本项目使用阿里云云效（Codeup 代码管理 + Projex 项目协作）进行迭代、需求、任务和代码评审管理。
> 本文基于 2026 年 10 月 AI PR Review 项目的实际操作整理，目标是让后续成员在最短时间内接手云效管理。
> 文中不包含任何真实令牌；示例 ID 为当前项目实例，迁移或重建项目后需要重新查询。

---

## 1. 一分钟上手

### 1.1 环境变量

| 变量 | 用途 | 示例 |
| --- | --- | --- |
| `ALIBABA_CLOUD_YUNXIAO_ACCESS_TOKEN` | 云效个人访问令牌（`pt-` 开头） | 已配置在系统环境变量中，勿提交仓库 |
| `ALIBABA_CLOUD_YUNXIAO_API_BASE_URL` | 云效实例域名（不带 `https://`） | `yitihuashijian-cn-hangzhou.devops.aliyuncs.com` |

令牌需要具备对应权限点：

- **代码管理**：仓库读写、保护分支读写、合并请求读写
- **项目协作**：项目只读、项目成员只读、迭代读写、工作项读写

如果接口返回 `403`，优先检查令牌权限点是否勾选，而不是怀疑代码。

### 1.2 连通性验证（PowerShell）

```powershell
$t = $env:ALIBABA_CLOUD_YUNXIAO_ACCESS_TOKEN
$b = "https://$env:ALIBABA_CLOUD_YUNXIAO_API_BASE_URL"
$h = @{ 'x-yunxiao-token' = $t }

Invoke-RestMethod -Uri "$b/oapi/v1/projex/projects:search" `
  -Method Post -Headers $h `
  -ContentType 'application/json; charset=utf-8' `
  -Body ([Text.Encoding]::UTF8.GetBytes('{"page":1,"perPage":20}'))
```

能返回项目列表即表示令牌和网络正常。

> 注意：PowerShell 直接传中文字符串时容易变成 `?`，涉及中文标题/描述务必使用 `UTF8.GetBytes`，或改用 Node.js 脚本。

### 1.3 统一请求约定

- 所有 Projex / Codeup 新接口以 `/oapi/v1` 开头。
- 认证统一使用请求头：`x-yunxiao-token: pt-...`。
- JSON 请求统一使用 `Content-Type: application/json; charset=utf-8`。
- 时间日期提交使用 `YYYY-MM-DD`；接口返回通常是毫秒时间戳。
- 列表接口注意分页上限：`page * perPage` 不得超过 10000，`perPage` 最大 200。

## 2. 核心对象模型

云效 Projex 的推荐组织方式是「模块 → 需求 → 任务」三层树：

```text
项目 Project
├── 迭代 Sprint（通过工作项的 sprint 字段归属，不是父节点）
│   ├── 迭代一（日期范围）
│   ├── 迭代二
│   └── 迭代三
└── 工作项树
    ├── M1 模块（Req，根节点，不挂迭代）
    │   ├── F01 功能需求（Req，挂迭代）
    │   │   ├── F01-FE 前端任务（Task）
    │   │   └── F01-BE 后端任务（Task）
    │   └── ...
    ├── M8 技术需求（Req → D01-D07 → 前后端任务）
    └── M9 项目过程与验收（T/A 任务）
```

关键理解：

- **迭代是工作项的一个字段**，不是工作项的父级。创建任务时传 `sprint: <sprintId>`。
- **模块节点**用于分组，不设置 `sprint`，保持为根节点。
- 一个工作项只有一个 `assignedTo`（负责人），多人协作通过 `participants`（参与人）+ 子任务实现。
- 根节点的 `parentId` 在查询结果中可能返回字符串 `"EMPTY_VALUE"`，不是 `null`；判断层级优先看 `idPath`。
- 子任务的 `parentId` 指向需求，需求的 `parentId` 指向模块，形成三层 `idPath`。

## 3. 标准操作流程（SOP）

### 3.1 找到项目

项目列表没有 `GET /projects`，使用搜索接口：

```http
POST /oapi/v1/projex/projects:search
Content-Type: application/json; charset=utf-8
x-yunxiao-token: <token>

{
  "page": 1,
  "perPage": 50,
  "orderBy": "gmtCreate",
  "sort": "desc",
  "conditions": "",
  "extraConditions": ""
}
```

返回字段中重点关注：

- `id`：项目唯一标识，后续所有 Projex 接口的 `spaceId`
- `name`：项目名称
- `customCode`：项目编号（如 `HAKT`）
- `status.name`：项目状态

查询单个项目：

```http
GET /oapi/v1/projex/projects/{projectId}
```

### 3.2 读取成员和工作项类型

```http
GET /oapi/v1/projex/projects/{projectId}/members
GET /oapi/v1/projex/projects/{projectId}/workitemTypes?category=Req
GET /oapi/v1/projex/projects/{projectId}/workitemTypes?category=Task
GET /oapi/v1/projex/projects/{projectId}/workitemTypes?category=Bug
```

成员返回 `userId`（UUID）和 `userName`，后续 `assignedTo`、`participants`、`owners` 都使用这个 `userId`。

工作项类型返回 `id` 和 `categoryId`。创建前必须先查，不要硬编码类型 ID。

### 3.3 查看和创建迭代

查看：

```http
GET /oapi/v1/projex/projects/{projectId}/sprints
```

创建：

```http
POST /oapi/v1/projex/projects/{projectId}/sprints
Content-Type: application/json; charset=utf-8
x-yunxiao-token: <token>

{
  "name": "迭代一：需求设计与 PR 接入",
  "description": "完成需求、数据库、UI 设计和 PR 接入验证。",
  "owners": ["<user-uuid>"],
  "startDate": "2026-10-12",
  "endDate": "2026-10-18"
}
```

更新：

```http
PUT /oapi/v1/projex/projects/{projectId}/sprints/{sprintId}
```

更新字段与创建基本一致，可调整名称、描述、负责人、起止日期；状态字段以当前 API 文档为准。

迭代规划建议：

- 每个迭代有明确起止日期，不要留空档。
- 答辩前最后一个迭代预留联调、修复和材料准备时间。
- 迭代负责人至少包含项目管理员。

### 3.4 创建需求树

**第一步：创建模块节点**

```json
{
  "assignedTo": "<项目负责人 userId>",
  "spaceId": "<projectId>",
  "subject": "M1 PR 接入与任务管理",
  "workitemTypeId": "<Req 类型 id>",
  "participants": ["<另一成员 userId>"],
  "formatType": "MARKDOWN",
  "description": "## 模块目标\n...\n\n## 包含内容\n- F01 ...\n\n## 模块验收\n- ..."
}
```

模块不传 `sprint`，作为根节点。

**第二步：创建需求**

```json
{
  "assignedTo": "<负责人 userId>",
  "spaceId": "<projectId>",
  "subject": "F01 输入 PR",
  "workitemTypeId": "<Req 类型 id>",
  "sprint": "<迭代一 sprintId>",
  "parentId": "<M1 模块 id>",
  "participants": ["<协作成员 userId>"],
  "formatType": "MARKDOWN",
  "description": "## 目标\n...\n\n## 功能要点\n- ...\n\n## 验收标准\n- ...\n\n## 分工\n- 前端：...\n- 后端：..."
}
```

技术需求 `D01-D07` 使用技术类需求类型；功能需求 `F01-F27` 使用产品类需求类型。

**第三步：创建前后端子任务**

```json
{
  "assignedTo": "<具体执行人 userId>",
  "spaceId": "<projectId>",
  "subject": "F01-FE 首页 PR 输入与基本信息展示",
  "workitemTypeId": "<Task 类型 id>",
  "sprint": "<与父需求相同的 sprintId>",
  "parentId": "<F01 需求 id>",
  "formatType": "MARKDOWN",
  "description": "## 任务目标\n...\n\n## 实施要点\n- ...\n\n## 完成标准\n- ...\n\n## 依赖\n..."
}
```

子任务的 `sprint` 必须与父需求一致，避免出现「需求在迭代一、任务不在迭代」的断链。

### 3.5 查询与校验

按类型搜索工作项：

```http
POST /oapi/v1/projex/workitems:search
Content-Type: application/json; charset=utf-8
x-yunxiao-token: <token>

{
  "category": "Req",
  "spaceId": "<projectId>",
  "spaceType": "Project",
  "page": 1,
  "perPage": 200
}
```

批量创建后至少检查：

- 模块、F/D 需求数量是否与规划一致
- 是否有重复 `subject`
- 每个非模块工作项是否有 `sprint`
- 每条需求是否有子任务，子任务 `parentId` 是否正确
- 每个工作项是否有 `assignedTo`
- `idPath` 是否呈现「模块 → 需求 → 任务」三层

查询单条工作项：

```http
GET /oapi/v1/projex/workitems/{workitemId}
```

### 3.6 更新工作项

```http
PUT /oapi/v1/projex/workitems/{workitemId}
Content-Type: application/json; charset=utf-8
x-yunxiao-token: <token>

{
  "status": "<statusId>",
  "assignedTo": "<userId>",
  "priority": "<priorityId>"
}
```

状态、优先级字段值不要猜，先通过工作项类型字段配置接口或已有工作项获取。

## 4. 命名与粒度规范

### 4.1 命名前缀

| 前缀 | 含义 | 示例 |
| --- | --- | --- |
| `M1`–`M9` | 模块/需求组 | `M1 PR 接入与任务管理` |
| `F01`–`F27` | 功能需求 | `F03 启动分析` |
| `D01`–`D07` | 开发/技术需求 | `D05 质量验证` |
| `T01`–`T08` | 过程任务 | `T02 数据库概念与逻辑设计` |
| `A01`–`A06` | 验收任务 | `A01 端到端演示` |
| `-FE` | 前端子任务 | `F20-FE Diff 查看器与风险行联动` |
| `-BE` | 后端子任务 | `F20-BE Diff 数据与行号映射接口` |

### 4.2 粒度原则

- **模块级**：按业务域划分，数量控制在 7–10 个，只做分组，不挂迭代。
- **需求级**：一条需求描述一个可验收的能力，保留原始编号 F/D。
- **任务级**：一条任务由一个人在一个短周期内完成；如果任务还需要再拆，说明粒度不够细。
- 前后端都涉及的需求，必须拆出 `-FE` 和 `-BE` 两个任务，分别指定负责人。
- 不要把「设计、开发、测试、部署」混在一条任务里。

### 4.3 需求描述模板

```markdown
## 目标
一句话说明要解决什么问题、交付什么能力。

## 功能要点
- 用户可感知的行为
- 关键交互/接口
- 异常与边界

## 验收标准
- 可现场演示或可自动验证的结果
- 正常、空、失败、部分完成状态

## 分工
- 前端：...
- 后端：...
```

### 4.4 任务描述模板

```markdown
## 任务目标
一句话说明这条任务完成后会得到什么。

## 实施要点
- 具体要改的页面/接口/数据表
- 关键实现步骤
- 需要处理的异常

## 完成标准
- 可检查的完成条件
- 测试或演示方式

## 依赖
依赖的需求、接口、数据或环境。
```

> 描述写得细，答辩和交接时不需要再靠口头解释。任务标题要能独立看懂，不要只写「优化」「联调」。

## 5. 负责人分配规则

本项目采用以下规则：

| 需求类型 | 负责人 | 参与人/子任务 |
| --- | --- | --- |
| 纯后端 | `root` | 无 |
| 纯前端 | `程磊` | 无 |
| 前后端都有 | 按主责设置负责人 | 另一人设为参与人，并拆出 `-FE` / `-BE` 子任务 |
| 模块节点 | 项目负责人 | 另一名成员作为参与人 |
| 过程/验收任务 | 按主责设置 | 需要双方参与时加参与人 |

说明：

- 云效一个工作项只有一个 `assignedTo`，所以「都分配」落地为「负责人 + 参与人 + 两个子任务」。
- 子任务负责人必须具体到人，不能挂在需求上不拆。
- 模块节点的负责人只用于显示归属，不代表具体开发工作。

## 6. 迭代规划模板

以本项目 2026 年 10 月为例：

| 迭代 | 日期 | 目标 | 关键内容 |
| --- | --- | --- | --- |
| 迭代一 | 10-12 ~ 10-18 | 需求、数据库、UI 设计 + PR 接入 | 需求说明、ER 图、表设计、页面原型、GitHub API 验证、F01–F02、D01/D07 |
| 迭代二 | 10-19 ~ 10-24 | AI 分析与评审工作台 + 中期答辩 | F03–F14、F19–F21、D02–D04、中期材料 |
| 迭代三 | 10-25 ~ 10-31 | 账户配置、主题双语、测试交付 + 结项答辩 | F15–F18、F22–F27、D05–D06、A01–A06、结项材料 |

规划原则：

- 中期答辩（10-24）前必须能演示「输入 PR → 获取真实变更 → 生成总结/风险 → Diff 定位 → 人工处理」的主链路。
- 结项答辩（10-31）前预留至少 2 天做联调、回归、部署和材料整理。
- 迭代二通常是核心冲刺，任务量会偏大；如果过重，优先把非演示必需的导出/对比功能移到迭代三。
- 需求、开发任务、缺陷都要有负责人、迭代和状态，答辩时才能展示完整过程。

## 8. 最小 Node.js 客户端

项目中涉及大量中文标题和描述，推荐用 Node.js（Node 18+ 自带 `fetch`）而不是 PowerShell 拼 JSON。

```js
const base = `https://${process.env.ALIBABA_CLOUD_YUNXIAO_API_BASE_URL}`;
const token = process.env.ALIBABA_CLOUD_YUNXIAO_ACCESS_TOKEN;
const headers = {
  'x-yunxiao-token': token,
  'Content-Type': 'application/json; charset=utf-8',
};

async function api(path, options = {}) {
  const res = await fetch(`${base}${path}`, { headers, ...options });
  const text = await res.text();
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${text}`);
  return text ? JSON.parse(text) : null;
}

// 搜索项目
const projects = await api('/oapi/v1/projex/projects:search', {
  method: 'POST',
  body: JSON.stringify({ page: 1, perPage: 50 }),
});

// 创建迭代
const sprint = await api(`/oapi/v1/projex/projects/${projectId}/sprints`, {
  method: 'POST',
  body: JSON.stringify({
    name: '迭代一：需求设计与 PR 接入',
    owners: [userId],
    startDate: '2026-10-12',
    endDate: '2026-10-18',
  }),
});

// 创建工作项
const item = await api('/oapi/v1/projex/workitems', {
  method: 'POST',
  body: JSON.stringify({
    assignedTo: userId,
    spaceId: projectId,
    subject: 'F01 输入 PR',
    workitemTypeId: reqTypeId,
    sprint: sprint.id,
    parentId: moduleId,
    formatType: 'MARKDOWN',
    description: '## 目标\n...',
  }),
});
```

批量创建时建议：

- 每创建一条 `await sleep(150~250)`，避免触发限流。
- 对 `429/500/502/503/504` 做 2–4 次指数退避重试。
- 创建前先搜索一次现有工作项，按 `subject` 建立映射，实现幂等重跑。
- 每批结束后打印「创建成功/跳过/失败」数量和失败原因。

## 9. 常见坑与排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `GET /oapi/v1/projex/projects` 返回 404 | 项目列表没有 GET 接口 | 改用 `POST /projects:search` |
| 中文标题/描述变成 `?` | PowerShell 默认编码问题 | 使用 `UTF8.GetBytes` + `charset=utf-8`，或改用 Node |
| 根节点 `parentId` 是 `"EMPTY_VALUE"` | 云效根节点哨兵值 | 不要当普通 ID 处理；用 `idPath` 判断层级 |
| 创建的需求没有挂在模块下 | 创建时漏传 `parentId` | 先取模块 `id`，创建需求时传 `parentId` |
| 任务不在迭代里 | 子任务漏传 `sprint` | 子任务 `sprint` 与父需求保持一致 |
| 多人负责人只显示一个 | 云效只有单 `assignedTo` | 用 `participants` + 拆 `-FE`/`-BE` 子任务 |
| 评审人加不上 | `reviewerUserIds` 需要 `userId` UUID，不是数字 ID | 用 `person/REVIEWER` 接口传 UUID |
| 自审批无法通过 | 保护分支未允许创建者审批 | 保护规则设置 `isAllowSelfApproval: true` 和 `isAllowSourceBranchPushUserApproval: true` |
| 直接推 master 被拒绝 | 保护分支未开放推送角色 | 走分支 + MR；或按需配置 `allowPushRoles` |
| `/api/v4/...` 返回 HTML | 私有实例只开放 `/oapi/v1` 网关 | 使用 PAT + `/oapi/v1` 接口 |
| Git 连接 127.0.0.1 失败 | 本机代理未启动 | 启动代理，或临时 `git -c http.proxy= -c https.proxy= ...` |
| 搜索工作项超过 200 条 | 分页上限 | `perPage` 最大 200，`page * perPage <= 10000` |
| 令牌 403 | 令牌缺少项目协作/代码管理权限点 | 重新创建令牌并勾选对应权限 |

## 10. 保护分支与 MR 流程

### 10.1 创建 master 保护规则

```http
POST /oapi/v1/codeup/repositories/{repoId}/protectedBranches
Content-Type: application/json; charset=utf-8
x-yunxiao-token: <token>

{
  "branch": "master",
  "allowPushRoles": [],
  "allowPushUserIds": [],
  "allowMergeRoles": [40],
  "mergeRequestSetting": {
    "isRequired": true,
    "minimumApproval": 1,
    "isAllowSelfApproval": true,
    "isAllowSourceBranchPushUserApproval": true,
    "isRequireDiscussionProcessed": true,
    "isResetApprovalWhenNewPush": true,
    "mrMode": "general",
    "allowMergeRequestRoles": [40]
  }
}
```

- `40` 表示管理员角色，`30` 表示开发者。
- `allowPushRoles` 留空表示禁止直接推送，强制走 MR。
- 需要创建者自审批时，必须显式开启两个 `isAllow...` 开关。

### 10.2 推荐 MR 流程

```text
backend-dev 开发
  → git push origin backend-dev
  → 创建 MR（backend-dev → master）
  → 添加评审人（UUID）
  → 提交 PASS 评审
  → 合并（no-fast-forward）
  → 保留长期分支 backend-dev
```

关键点：

- MR 标题/描述如果出现 `?`，用 `PUT /changeRequests/{localId}` 重新以 UTF-8 写入。
- 创建 MR 时 `reviewerUserIds` 可能不生效，改用 `person/REVIEWER` 接口补评审人。
- 合并时 `removeSourceBranch` 对长期分支设为 `false`。
- 合并后本地 master 执行 `git fetch origin` + `git merge --ff-only origin/master`。

## 11. 安全与权限

- 令牌只放在环境变量或本地密钥管理中，**不得写入仓库、文档、日志或截图**。
- 按最小权限创建令牌，定期轮换；离职或交接时及时撤销。
- 日志中不得输出完整令牌、密码、私有代码或用户敏感信息。
- 共享屏幕/答辩演示前检查终端历史和环境变量，避免泄露密钥。
- 调用外部模型前，按项目需求提示「代码将发送至所配置服务」。
