# 后端答辩问答

## 认证与权限

**1. 为什么用 Sa-Token opaque token，不用 JWT？**
JWT 的撤销和刷新旋转要额外维护黑名单；本项目用 Redis 保存 access-token 会话和 refresh-token，退出/刷新/封禁可以立即失效。opaque token 不携带用户信息，服务端每次查 Redis。

**2. refresh-token 如何旋转？旧 token 为什么失效？**
刷新时先删除旧 refresh-token，再签发新 access + refresh；旧 token 再请求返回 401。多设备登录时退出会删除该用户全部 refresh-token。

**3. 如何防止横向越权？**
`TaskAccessService` 统一校验：登录用户必须是任务所有者，或持有匹配且未过期的 guestToken；删除/对比/设置只允许本人/登录角色。Controller 不自行判断归属。

**4. 游客链接安全吗？**
guestToken 是任务级 64 位 hex，默认 7 天；只能访问该任务及其子资源，不能列表/删除/对比/设置。过期返回 403；错误 token 不能枚举任务。

## 任务与状态

**5. 任务为什么会重复执行？怎么避免？**
创建用幂等键（Redis 10 分钟）+ 同用户同 PR 同 head SHA 运行中检查；worker 用条件更新 `WHERE status=1` claim，更新 0 行即跳过；进度/完成也只更新 `status=2`。

**6. 为什么不用 MQ？**
当前规模用固定 worker + 有界队列 + DB 状态足够，少一个基础设施；任务状态持久化，重启可恢复。未来并发/多实例可平滑换 MQ，TaskWorker 接口不变。

**7. 取消是怎么生效的？**
取消条件更新 status 1/2→6；worker 在每个阶段边界更新进度，如果状态已不是 2 就抛 `TaskCanceledException`；并发批次在边界检查并中断剩余 future。已产生的结果保留。

**8. 部分完成和失败有什么区别？**
部分完成 status=4 有报告，只是有跳过/失败文件或模型丢弃，errorCode 5/6/7；失败 status=5 是致命阶段错误，可能没有报告。两者都保留已入库数据，都可重试。

**9. 启动恢复怎么做？**
启动时 status=2 的任务统一改 5/errorCode=8“服务重启导致任务中断”；status=1 的排队任务重新投递。不会把运行中任务误标为完成。

## AI 分析

**10. 为什么分两阶段？**
阶段 1 先固定 PR 目的、变更和重点文件，阶段 2 再按批找问题；避免“边总结边找问题”导致上下文漂移，也方便控制批次上下文大小。

**11. 怎么防止模型编造文件和行号？**
只允许文件清单内的路径；行号必须落在 patch 新增行；无法定位降级报告级或丢弃；证据为空置信度≤60；重复问题合并。模型输出不直接透传前端。

**12. 工具循环会不会无限调用？**
每批最多 6 轮、8 次工具调用；没有调用提交工具先提醒一次，仍不调用则该批失败；工具只读、路径白名单、单文件 20KB，不执行 shell/任意网络。

**13. 大 PR 怎么控制成本和上下文？**
每批 3–5 文件，`batch-concurrency` 1–4（默认 2），文件数/Diff 行数有上限；单批失败隔离；批次进度 50–89；187 文件实测 60.1 秒。

**14. 为什么默认 v4.1 Flash 而不是 Pro？**
D02 用 5 个受控案例对比：两者结构化/schema/核心缺陷都 5/5；Flash 平均 6.0s/7,229 tokens，Pro 10.6s/7,916 tokens。Flash 更适合主链路，Pro 作为复杂 PR 可选。

**15. 模型误报怎么处理？**
严重度和置信度分开展示；低置信度/无证据标记待确认；人工可采纳/解决/误报/撤销；D05 记录了主观建议误报和样本限制；后续用反馈统计优化 prompt。

## 数据与一致性

**16. 报告、问题、行号如何保证同一版本？**
任务创建时固定 `analysis_task.head_sha`；PR 更新只改 `pull_request.head_sha` 并让旧报告 `isExpired=true`；报告/问题/文件都按 task_id 查询，不会混用新版本。

**17. 逻辑删除会不会漏过滤？**
`analysis_task.is_deleted=1` 后，任务列表/详情/子资源都走带 `is_deleted=0` 的查询；问题/文件通过 task 归属校验。删除接口只允许本人已结束任务。

**18. 并发写入问题会不会重复？**
问题入库在批次间串行化并做 `fileId+category+normalizedTitle` 去重；状态更新用条件 UPDATE；MySQL 唯一键/索引兜底。

## 工程与交付

**19. 为什么包结构参考 sky-take-out？**
单 Maven 模块按职责分包：异常进 `exception`、全局处理进 `handler`、任务引擎进 `task`、AI 编排进 `analysis`，避免 `service.ai` 这种含义不清的分包；不为了分层而拆多模块。

**20. 测试和指标有哪些？**
40/40 API/状态回归；D05 20+ 案例；真实模型 README 20.8s/4,504 tokens；已知缺陷 2/2 检出、行号 1/1；大 PR 184 analyzed/3 skipped/60.1s；部分 4/7、超时 5/6、恢复 5/8。指标和误报漏报都写入 `docs/测试用例与指标.md`。

**21. 部署怎么做？**
`backend/Dockerfile` 多阶段 JDK 17 + 非 root；`deploy/docker-compose.yml` 启动 MySQL/Redis/Backend/Nginx；Nginx 反代 `/api`；密钥走 `.env`，本地配置/日志/target 排除。当前机器无 Docker，目标机需复验构建和 `nginx -t`。

**22. 还有哪些没做？**
正式前端七类页面、主题/双语、F20/F22 前端交互由前端同学完成；Docker/Nginx 目标机实测、TLS/备份、跨文件真实 ground truth、增量评审和 GitHub 行内评论是后续项。我们不把“后端完成”说成“全项目完成”。
