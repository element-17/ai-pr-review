## 1. 开场必备

### 1.1 30 秒介绍

> 我们做的是一个 AI PR Review 助手平台。用户在网页输入公开 GitHub PR 链接，后端异步拉取 PR 元数据和 Diff，用两阶段 AI 分析生成 PR 总结、重点文件和候选问题，再经过文件/行号/证据校验后入库。用户可以按文件看 Diff、定位问题、采纳或标记误报，最后导出 Markdown 报告。核心目标不是替代评审人，而是让 AI 的结论**有版本、有证据、可追溯**。

### 1.2 1 分钟介绍

> 项目面向个人开发者和小团队。GitHub PR 的变更信息分散、Review 成本高，现有 AI 工具经常给出一段不可验证的总结。我们把流程做成任务：任务创建时固定 `head_sha`，后台异步拉取文件、补充函数级上下文，第一阶段生成总结和重点文件，第二阶段按批识别七类风险；模型输出必须经过文件归属、有效变更行、证据和重复校验，不能定位的问题降级为报告级或直接丢弃。报告、问题、行号和任务版本绑定，PR 更新后旧报告标记过期。权限上区分游客、登录用户和管理员，游客用任务级 token 分享，登录用户有历史记录和版本对比。当前后端主链路、40 项回归和真实模型样例已经跑通；正式前端和 Docker 目标机复验还在收尾。

### 1.3 三个数字 / 三件完成 / 三件未完成

- 三个数字：9 张表、6 个任务状态、40/40 API 与状态回归通过。
- 三件完成：GitHub 真实 PR 接入、异步任务状态机与部分完成、两阶段 AI 分析 + 校验入库。
- 三件未完成：正式前端七类页面、Docker/Nginx 目标机实测、更多真实模型/跨文件评测样本。

## 2. 需求与定位【权重 30% · P0 主线】

### Q01 ★ 为什么做这个项目？目标用户是谁？

> **答**：PR Review 的信息量大、上下文分散，人工容易漏看；通用 AI 聊天工具的输出又很难验证。我们做的是一个可追溯的评审工作台，目标用户是个人开发者和小团队。游客可以直接试用，登录用户可以保存历史、做版本对比。
>
> **追问**：为什么不是给大企业做？——大企业更倾向私有部署、权限体系和审计，我们当前是课程项目规模，先把公开 PR 的闭环跑通。

### Q02 ★ 和 CodeRabbit、SonarQube、Copilot 有什么区别？

> **答**：不比较功能强弱，定位不同。SonarQube 以规则静态扫描为主；Copilot 更偏对话式辅助；我们做的是“任务化 + 报告化 + 版本一致 + 人工反馈”的 PR 评审闭环，重点在模型输出的校验和可追溯，而不是宣称模型本身更强。

### Q03 ★ 核心业务流程是什么？

> **答**：输入 PR → 预览元数据 → 创建任务（固定 head SHA）→ 异步拉取文件 → 两阶段 AI 分析 → 字段/行号校验 → 报告与问题入库 → Diff 定位与人工反馈 → 导出 Markdown → PR 更新后旧报告过期、可重新分析。

### Q04 ★ 本期做了什么，明确不做什么？

> **答**：做：公开 PR 接入、任务状态机、异步分析、分层总结、重点文件、七类问题、证据/行号校验、报告、人工反馈、导出、版本对比、设置、游客分享、权限。不做：私有仓库 OAuth、自动发布 GitHub 行内评论、增量评审、Webhook 自动触发、测试代码生成。加分项都没做，先把核心闭环做完整。

### Q05 ★ 中期最低目标达到了吗？

> **答**：中期要求是“输入真实公开 GitHub PR，获取并展示元数据与文件 Diff”。我们不仅跑通了预览，还完成了任务创建、异步分析、报告和问题入库。现场可以演示 `octocat/Hello-World#11596`；网络异常时切 fake provider 的预创建任务兜底。
>
> **追问**：为什么提前做了后面的功能？——后端主链路是一个整体，任务状态机和校验不做，报告就不可信；前端页面和部署复验仍在按计划推进。

### Q06 ★ 需求是怎么分析和确认的？

> **答**：先把原始需求拆成 F01–F27、B01–B04、D01–D07、A01–A06，再按“平凡/非平凡”分类。非平凡需求先做数据模型、状态机、接口契约和错误码，再写代码；平凡需求复用统一骨架。每项实现都能在 `docs/非平凡需求设计说明.md`、接口文档和测试用例里对应到编号。

### Q07 ★ 怎么保证需求不跑偏？

> **答**：用编号追踪：需求编号 → 设计文档 → 接口/代码 → 测试用例。答辩材料里也有实现索引。范围变化时先改文档和任务，不在代码里临时加需求。比如私有仓库、GitHub 评论都明确列为本期不做。

### Q08 ★ 为什么游客也能用？会不会被滥用？

> **答**：游客模式降低试用门槛，适合公开 PR 分享。限制是：任务级 64 位随机 token、默认 7 天过期、只能访问该任务及子资源，不能列表/删除/设置/对比；创建任务按 IP 限制 5 次/小时，预览 30 次/分钟。
>
> **边界**：游客不能查历史，也不做同 PR 运行中任务的去重，极端情况下可能重复创建；后续可以加游客维度的运行中检查或分布式锁。

### Q09 ★ 为什么报告语言是任务级，而不是跟随界面语言？

> **答**：报告是历史产物，必须可复现。任务创建时把 `report_language` 固定下来，AI 按这个语言生成；切换界面语言只改 UI，不改写历史报告。要另一种语言就重新分析一个任务。

### Q10 ★ 为什么同版本要复用已有结果？

> **答**：任务由仓库、PR 编号和 `head_sha` 唯一确定。同用户、同 PR、同 head SHA 且状态为完成/部分完成时，预览会提示可复用，避免重复调用模型、重复计费。运行中的同版本任务会返回 409。

### Q11 ★ 需求优先级怎么排？

> **答**：先保证非平凡主链路：PR 接入、任务状态机、AI 分析、校验、报告/问题/反馈、权限；再做设置、历史、导出、版本对比；最后是主题/双语、部署和体验优化。加分项不挤占核心工期。

### Q12 ★ 现在进度如何？有没有落后？

> **答**：后端主链路和测试材料已经完成并合并，前端联调页可用，正式前端和 Docker 目标机复验还在收尾。中期最低演示目标已经达到；剩余工作主要是前端页面、响应式/主题/双语和部署复验，不把“后端完成”说成“全项目完成”。

### Q13 团队怎么分工？

> **答**：（按你们实际情况填：后端、前端、测试/文档、云效管理。）我负责的部分是……，代码和设计决策都能解释；AI 辅助只用于提效，提交前都经过运行和检查。

## 3. 数据库设计【权重 25% · P0 主线】

### Q14 ★ 画一下 ER 图，为什么是 9 张表？

> **答**：`user` 1–1 `user_github_binding`；`user` 1–1 `user_setting`；`user` 1–N `analysis_task`；`ai_model_config` 可选引用 `user_setting.preferred_model_id` 和 `analysis_task.model_config_id`；`pull_request` 1–N `analysis_task`；`analysis_task` 1–N `task_file`、1–1 `analysis_report`、1–N `review_issue`；`task_file` 1–N `review_issue`（报告级问题 `file_id` 为空）。9 张表覆盖“账号/身份绑定/模型配置/设置/PR/任务/文件/报告/问题与反馈”，没有为展示再拆表。

### Q15 ★ 为什么 PR 元数据要单独建表？

> **答**：同一个 PR 会被多次分析，元数据可以复用；`repo_full_name + pr_number` 唯一，避免重复行。表里保存最新 `head_sha`，任务表保存创建时的 `head_sha`，两者比较就能判断报告是否过期。

### Q16 ★ 为什么任务表存 `head_sha`，不建 commit 表？

> **答**：当前只需要“这次分析对应哪个提交”，不存 commit 的完整历史，单独建表会增加 join 和维护成本。`head_sha` 是不可变快照，报告、文件、问题都挂在任务下，天然同版本。将来要做增量评审，再引入 commit/文件指纹表。

### Q17 ★ `analysis_config` 为什么用 JSON？

> **答**：它是任务创建时的非敏感配置快照（检查类别、忽略目录、文件/Diff 上限等），字段会随设置项变化。用 JSON 避免为每个配置拆列或建表，也保证历史任务不受后续设置修改影响。MySQL 8 原生支持 JSON；如果将来要按配置检索，可以加生成列和索引。

### Q18 ★ `task_file.patch` 这么大，为什么放 MySQL？

> **答**：patch 是任务的核心证据，和文件行、问题行号强关联，放一起便于事务和级联查询。我们有上限：单文件 patch 200,000 字符、单任务默认 200 文件/20,000 Diff 行；二进制、无 patch、超大文件会保留文件行并标记跳过及原因。更大的场景可以把 patch 放对象存储，数据库只存引用。

### Q19 ★ 索引是怎么设计的？依据是什么？

> **答**：按真实查询路径设计：`idx_status` 给调度器扫排队任务；`idx_user_time` 给历史列表；`idx_user_pr_time` 给复用/运行中检查；`idx_pr_sha_user` 给同 PR 同版本查询；`idx_task_feedback` 给问题按状态/严重度筛选；`idx_expire_time` 给游客过期清理预留。唯一键包括用户名、`repo+pr_number`、`task_id+file_path`、`task_id`（报告）、`guest_token`。复杂筛选用 Mapper XML，单表 CRUD 用 MyBatis-Plus。

### Q20 ★ 外键为什么有的 CASCADE、有的 RESTRICT？

> **答**：`analysis_task → pull_request/user` 用 RESTRICT，防止误删还有任务引用的 PR/用户；`task_file/analysis_report/review_issue → analysis_task` 用 CASCADE，任务物理清理时子数据一起清；`review_issue → task_file` 也是 CASCADE；`feedback_user_id → user` 用 SET NULL，用户删除后反馈保留但操作人置空。任务删除本身是逻辑删除，所以平时不会触发级联，查询都通过任务归属过滤。

### Q21 ★ 逻辑删除怎么做的？为什么有的表没有？

> **答**：`user.deleted` 和 `analysis_task.is_deleted` 用 MyBatis-Plus `@TableLogic` 自动过滤；`analysis_task` 的列名是 `is_deleted`，实体里显式 `@TableField("is_deleted")` 覆盖全局 `deleted` 配置。`task_file/report/issue` 不做逻辑删除，它们通过任务访问，任务逻辑删除后自然不可见；物理清理任务时由外键 CASCADE 处理。`pull_request` 和 `user_setting` 也不做，前者是共享元数据，后者 PK 就是 user_id。

### Q22 ★ 为什么反馈直接放在 `review_issue`，不建反馈历史表？

> **答**：当前需求只保留“最新处理状态 + 处理人 + 时间”，1:1 放同表查询和导出最简单。代价是没有反馈历史，撤销会覆盖当前建议；如果要做质量闭环和审计，再加 `review_issue_feedback` 历史表。

### Q23 ★ 事务边界怎么划的？有没有长事务风险？

> **答**：创建任务在一个事务里写 PR upsert + task；worker 的 claim、进度、完成都是条件 UPDATE；问题入库在事务里做去重和插入，并用批次保存锁串行化；反馈/撤销也是短事务。
>
> **追问：创建事务里调用 GitHub 会不会太长？** 会。当前 QPS 低，可以接受；严格做法是把 GitHub 调用移到事务外，或先落“待创建”记录再异步补元数据，缩短数据库连接持有时间。这是已知优化点。

### Q24 ★ 数据量涨了怎么办？

> **答**：`task_file.patch` 和 `review_issue` 是主要增长点。短期靠任务级上限和游客过期控制；中期可以按 `create_time` 归档已完成任务、把 patch 移到对象存储；长期按任务/时间分区。当前没有自动清理游客过期任务的定时任务，`idx_expire_time` 是为后续清理预留的，这点要如实说。

### Q25 ★ 为什么用 MySQL，不用 MongoDB？

> **答**：任务、报告、问题、反馈之间有明确关系和唯一约束，需要事务和 join；MySQL 更合适。JSON 只用于配置快照，不承担主要查询。MongoDB 的灵活 schema 在这里不是优势，反而弱化一致性。

### Q26 ★ 建表脚本和自动填充在哪里？

> **答**：`deploy/sql/schema.sql` 和 `backend/src/main/resources/db/schema.sql` 是初始化脚本，包含字段注释、索引、外键、字符集；`BaseEntity` + `MyMetaObjectHandler` 自动填充 `create_time/update_time/create_user/update_user`；分页和防全表更新在 `MybatisPlusConfig`。

## 4. 架构与技术选型

### Q27 ★ 整体架构和模块边界是什么？

> **答**：单 Maven 模块，按职责分包：`controller` 只做参数和响应；`service/service.impl` 负责业务、权限、事务；`task` 是调度和 worker；`core/analysis` 是 AI 编排和校验；`core/agent` 是模型客户端和工具循环；`core/github` 是 GitHub 协议；`mapper/pojo` 是持久化；`common` 放常量、异常、结果、日志、配置。外部集成不混进 Controller。

### Q28 ★ 为什么单体，不拆微服务？

> **答**：当前团队和流量规模不需要微服务。单体部署简单、事务好控制、调试成本低；包边界已经按职责拆开，将来真要把任务引擎或 AI 分析拆出去，接口和状态机可以复用。为微服务而微服务会增加网络、部署和一致性成本。

### Q29 ★ 为什么用 Spring Boot 4 和 Java 17？

> **答**：新项目直接采用当前主线，避免一开始就背历史包袱；Sa-Token 和 MyBatis-Plus 都有 Spring Boot 4 的 starter，项目已编译、测试通过。Java 17 是基线，本地测试也跑过更高版本 JDK。风险是新版本资料少，所以关键依赖都锁定版本并做了回归。

### Q30 ★ 为什么用 MyBatis-Plus，不用 JPA？

> **答**：需求里大量是条件筛选、分页、逻辑删除和自动填充，MyBatis-Plus 的条件构造器和分页插件更直接；复杂查询仍可写 XML，SQL 可控。JPA 的实体关系映射在这里反而增加隐式行为。

### Q31 ★ 接口返回为什么统一 `{code,message,data}`？HTTP 状态码呢？

> **答**：项目规范要求统一响应体，前端只按 `code` 分支。业务异常（参数、权限、业务冲突）多数返回 HTTP 200 + body 里的业务码；静态资源等框架异常才用 HTTP 404。代价是不够严格 RESTful；如果评委要求，可以改成 `ResponseEntity` 把业务码映射到 HTTP 状态，前端拦截器同步调整。

### Q32 ★ Redis 都用来做什么？Redis 挂了会怎样？

> **答**：四类用途：Sa-Token 会话与 refresh-token、登录失败计数、接口/游客限流、任务创建幂等键、PR 预览缓存。Redis 挂了：登录/鉴权会失败（这是硬依赖）；限流会放行；幂等键降级为不缓存；预览缓存回源 GitHub。不会造成数据写坏，但可用性受影响，生产需要 Redis 高可用。

### Q33 ★ 为什么不用 MQ？

> **答**：当前规模用“数据库状态 + 定时扫描 + 条件 claim + 固定线程池”就够了，少一个基础设施，任务状态天然可恢复。MQ 的优势是削峰和投递可靠性；将来并发上来可以替换 dispatcher，TaskWorker 接口不用变。

### Q34 ★ 为什么每 5 秒扫一次？延迟是不是很大？

> **答**：5 秒是 `fixedDelay`，扫 `status=1` 的最多 20 条，投递到 2 个 worker 的有界队列。任务本身 AI 分析通常 20 秒以上，5 秒启动延迟占比不高；同时避免创建接口同步触发、重启丢任务。间隔可配 `pr.task.dispatch-interval-ms`。如果要更低延迟，可以在事务提交后用 `afterCommit` 按 taskId 投递一次，定时扫描保留兜底。

### Q35 ★ 线程池参数怎么定的？队列满了怎么办？

> **答**：默认 2 个 worker、队列 100，`ThreadPoolTaskExecutor` 有界，避免无限堆积。队列满时 `TaskRejectedException` 被捕获，日志提示“等待下一轮调度”，任务仍在 `status=1`，下一轮继续。单个 worker 内部 AI 批次并发默认 2，所以最坏同时 4 个模型请求；参数都可配。

### Q36 ★ 多实例部署会不会重复执行同一个任务？

> **答**：不会重复执行业务。claim 是 `UPDATE ... SET status=2 WHERE id=? AND status=1`，只有一行更新成功，其他实例/线程更新 0 行直接返回。重复投递会浪费线程池槽位和一次 UPDATE，但不会重复写报告/问题。更彻底可以做 dispatcher 选主或按任务分片。

### Q37 ★ 为什么用轮询，不用 SSE/WebSocket？

> **答**：轮询实现简单、穿代理稳定、刷新后状态不丢；前端 2 秒查一次 `/progress`，到终态停止。SSE 更适合大量并发实时推送，但要处理连接保活、代理缓冲和多实例路由，当前规模不值得。后续可以加 SSE 作为可选通道，状态仍以数据库为准。

### Q38 ★ 日志和可观测性怎么做的？

> **答**：每个请求生成/透传 `X-Request-Id`，写入 MDC；worker 用 `task-{id}` 作为 traceId；访问日志只记录方法、路径、状态、耗时、IP、用户 ID，不记录 query、请求体、请求头和响应体；日志布局统一做脱敏；SQL DEBUG 只在 dev 打开；模型只记录 token 数和耗时，不记录 prompt/代码。

### Q39 ★ 配置和密钥怎么管理？

> **答**：真实数据库密码、GitHub Token、模型 Key 只放本地 `application-dev.yml`、环境变量或 `deploy/.env`，这些文件都在 `.gitignore` / `.dockerignore`；仓库只有 `.example` 占位符。Docker 镜像非 root，MySQL/Redis 不映射宿主机端口；生产还必须改默认账号密码、接 TLS 和密钥管理。

### Q40 ★ 前端技术选型和请求封装？

> **答**：联调前端用 Vue 3 + Element Plus + Vite + axios + vue-router；`api.js` 集中封装请求和错误处理，`store.js` 管登录态/主题/语言，`i18n.js` 管中英文，`DiffViewer` 等组件拆分。没有引入 Pinia，是因为联调页状态简单，避免额外依赖；正式前端可以按团队规范升级。

## 5. GitHub 接入【权重 10% · P0 第三方验证】

### Q41 ★ GitHub 接口怎么接的？用了哪些 API？

> **答**：服务端用 GitHub REST API，PAT 放在服务端配置里。主要接口：PR 元数据、PR 文件列表（`per_page=100`，最多 30 页）、PR commits（2 页）、按固定 `head_sha` 读文件内容。预览结果在 Redis 缓存 60 秒，创建任务时重新拉取 head SHA，保证版本一致。

### Q42 ★ 私有仓库支持吗？Token 权限怎么控制？

> **答**：当前只支持公开 PR，没有做 GitHub OAuth，所以没有私有仓库授权链路。Token 只在服务端使用，不进前端、不进日志；公开仓库无 Token 也能跑，但限额只有 60 次/小时，配 Token 后 5,000 次/小时。私有仓库和授权撤销是后续 X04。

### Q43 ★ GitHub 限流怎么处理？

> **答**：区分 429 和 403：403 且 `X-RateLimit-Remaining=0` 或带 `Retry-After` 视为限流，映射为任务错误码 2；普通 403 是权限问题，映射为 3。429/5xx 最多重试 2 次，优先按 `Retry-After` 等待（上限 5 秒），否则线性退避 500ms×次数。404/422 映射为 PR 无效。用户看到明确原因和重试入口，不会无限重试。

### Q44 ★ 超时怎么设的？

> **答**：GitHub 连接 5 秒、读取 30 秒；模型连接 10 秒、读取 180 秒。所有外部调用都有上限，失败落到任务错误码，不会让 worker 永久挂住。文件内容单次最多 200,000 字符，路径拒绝绝对路径和 `..`。

### Q45 ★ 大 PR 怎么拉取和截断？

> **答**：文件列表按 100 条/页、最多 30 页；任务级默认最多 200 个文件、20,000 Diff 行，单文件 patch 上限 200,000 字符。超限文件保留记录并写 `skip_reason`，任务最终是部分完成，不会 OOM 或无限等待。实测 187 文件在并发 2 下 60.1 秒完成。

### Q46 ★ 重命名、删除、二进制、无 patch 怎么处理？

> **答**：GitHub 的 `status` 映射为新增/修改/删除/重命名/复制，重命名保留 `old_path`；二进制按扩展名识别，直接跳过；GitHub 未返回 patch 也跳过；删除文件没有新文件侧行号，相关问题降级为报告级。所有跳过都会在报告覆盖范围里显示原因。

### Q47 ★ 怎么保证报告、问题和行号是同一个版本？

> **答**：创建任务时固定 `analysis_task.head_sha`，之后所有文件内容、patch、行号都基于这个 SHA；`pull_request.head_sha` 只用于详情页比较，返回 `isExpired`。报告/文件/问题都按 `task_id` 查询，不会混用新版本；PR 新提交后旧报告仍可查看但标记过期，重新分析会创建新任务。

### Q48 ★ 预览缓存 60 秒，会不会拿到旧数据？

> **答**：预览缓存只用于展示，允许 60 秒内的元数据旧值；创建任务时会重新调用 GitHub 获取最新 head SHA，并固定到任务。所以缓存不会影响分析版本。

### Q49 ★ 第三方接入做过什么验证？

> **答**：用真实公开 PR 验证过：`octocat/Hello-World#11596`（普通文档修改、已知拼写缺陷）和 `vercel/next.js#100042`（187 文件大 PR）。验证内容包括元数据、文件清单、patch、限流/404/超时映射和任务状态落库；记录在 `docs/测试用例与指标.md` 和 `docs/全量业务回归与状态验证.md`。

## 6. 异步任务与状态机

### Q50 ★ 任务状态机是什么？

> **答**：`1 排队 → 2 分析中 → 3 完成 / 4 部分完成 / 5 失败 / 6 取消`。阶段是 `1 排队 → 2 获取 PR → 3 获取变更 → 4 补上下文 → 5 AI 分析 → 6 校验入库 → 7 结束`。终态都写 `finish_time`；部分完成有报告但保留跳过/失败原因；失败是致命错误，可能没有报告。

### Q51 ★ 为什么用数据库当队列？

> **答**：任务状态必须持久化，刷新、重启、多实例都要能看到；数据库本身就是唯一事实来源。定时扫描 + 条件 claim 实现简单，少一个 MQ。缺点是有最多 5 秒启动延迟和空轮询查询，当前规模可接受。

### Q52 ★ claim 是怎么做的？为什么能防重复？

> **答**：worker 执行前先执行 `UPDATE analysis_task SET status=2, stage=2, progress=5, start_time=now WHERE id=? AND status=1 AND is_deleted=0`；更新 1 行才继续，0 行说明已被别的 worker 抢走、已取消或已删除，直接返回。进度/完成也只更新 `status=2`，避免覆盖取消状态。

### Q53 ★ 取消是怎么生效的？

> **答**：取消是条件更新 `status in (1,2) → 6`，重复取消幂等。worker 在每个阶段边界更新进度，如果更新 0 行就抛 `TaskCanceledException`；批次循环也会检查状态并中断剩余批次。已经生成的报告/问题保留，用户仍可查看。
>
> **追问：正在调模型时能立刻停吗？** 不能中断已经发出的 HTTP 请求，会在下一个边界停止；这次调用仍可能消耗 token，这是边界。

### Q54 ★ 重试和幂等怎么做的？

> **答**：重试只允许 4/5/6，新建一条 `status=1` 任务，复制 PR、head SHA、语言、配置和模型，记录 `retry_of_task_id`；旧任务和旧 token 不删除。创建/重试支持 `Idempotency-Key`：Redis 存请求哈希和首次响应 10 分钟，同 key 同请求返回同一结果，不同请求体返回 409。
>
> **边界**：幂等缓存写在事务内，极端回滚下可能出现“缓存有、数据库没有”的短窗口；后续可改成事务提交后写缓存。

### Q55 ★ 部分完成和失败有什么区别？

> **答**：部分完成 `status=4` 有报告，只是有跳过/失败文件、批次失败或校验丢弃，`errorCode` 通常是 5/6/7；失败 `status=5` 是致命阶段错误，可能没有报告。两者都保留已入库数据，都允许重试。这个区分是为了避免把“没分析全”说成“成功”。

### Q56 ★ 服务重启后任务怎么办？

> **答**：启动时 `TaskRecoveryRunner` 把所有 `status=2` 的任务标成 `5/errorCode=8`，提示“服务重启导致任务中断”；`status=1` 的排队任务保留，并立即触发一次 dispatch，不用等下一个 5 秒周期。不会把运行中任务误标为完成。

### Q57 ★ 任务会不会永久卡住？

> **答**：所有外部调用都有超时（GitHub 30 秒、模型 180 秒），批次失败会落到部分完成/失败；进程重启有恢复逻辑。没有单独的心跳 watchdog，如果线程被非超时因素挂住，当前只能靠重启恢复；后续可以加 `update_time` 超时扫描。

### Q58 ★ 游客重复创建同一个 PR 怎么办？

> **答**：登录用户会检查同 PR 同 head SHA 的运行中任务并返回 409；游客目前只靠 IP 限流 5 次/小时，没有做同版本去重，所以理论上可以创建多个任务。这是已知边界，后续可以加游客维度的 Redis 锁或运行中检查。

### Q59 ★ 进度是怎么更新的？

> **答**：创建时 0，claim 后 5，获取 PR/文件/上下文/AI/校验分别推进到 10/20/35/50，问题批次完成在 50–89 之间递增，终态 100。每次更新只改 `status=2` 的任务，取消后更新失败即停止。前端 2 秒轮询，进入终态停止。

## 7. AI 分析与可信度

### Q60 ★ 为什么分两阶段？

> **答**：第一阶段先固定 PR 目的、主要变更、影响模块和重点文件，形成全局视角；第二阶段按文件批次找问题。这样第二阶段有稳定的总结上下文，不会“边总结边找问题”导致上下文漂移，也方便每批控制 token。第一阶段失败是致命失败，不生成假报告。

### Q61 ★ Agent 工具循环怎么工作？会不会无限调用？

> **答**：模型可以通过 `submit_summary` / `submit_issues` 提交结构化结果，也可以调用只读工具 `read_file`、`find_callers`、`read_tests`。每批最多 6 轮、8 次工具调用；如果没有调用提交工具，先提醒一次，仍不调用则该批失败。工具只读、路径白名单、单文件 20KB，不执行 shell、不访问任意网络。

### Q62 ★ 结构化输出怎么保证？

> **答**：工具参数有 JSON schema，后端解析成 `IssueDraft`；类别、严重度、置信度、必填字段都做范围校验，不合法直接丢弃。模型输出不会原样透传给前端，也不会直接入库。

### Q63 ★ 怎么防止模型编造文件和行号？

> **答**：文件必须属于当前任务的 `task_file` 清单；有文件的 issue 必须有起始行；`PatchLineIndex` 解析 patch，行号必须落在新文件侧新增行，完全不在 hunk 内会进一步降置信度；删除文件或没有新增行时降级为报告级；找不到文件、行号非法或字段缺失直接丢弃。

### Q64 ★ 行号是怎么映射的？

> **答**：`PatchDiffParser` 解析 `@@` hunk，维护旧/新行号；问题使用新文件侧行号。Diff 接口返回 `rows`，问题按 `newLine` 落在 `startLine–endLine` 区间映射 `issueIds`，前端只负责渲染，不重算行号。

### Q65 ★ 证据和置信度怎么处理？

> **答**：证据为空时置信度上限 60；行号不在新增行上限 50，不在 hunk 上限 40；严重度和置信度分开展示，低置信度标记“需人工确认”。高严重度低置信度不会被包装成确定缺陷。

### Q66 ★ 重复问题怎么去重？

> **答**：去重键是 `fileId（报告级用 report）+ category + 规范化标题`；入库时先读该任务已有问题构建 `seen` 集合，再对新问题去重；多个 AI 批次保存时用锁串行化，避免并发竞争。数据库没有为问题建唯一键，因为标题是自然语言，唯一键会误伤；当前用应用层去重。

### Q67 ★ 上下文是怎么补的？为什么只支持 TS/Python？

> **答**：`ContextBuilder` 按固定 `head_sha` 通过 GitHub Contents API 读文件，单文件 20KB，拒绝绝对路径和 `..`；`TypeScriptContextExtractor`/`PythonContextExtractor` 提取变更行所在函数、import，失败回退到变更行附近窗口。需求 F10 只要求至少一种语言，TS/Python 覆盖常见 Web 技术栈；其他语言仍能靠 patch 和窗口上下文分析，只是函数级能力弱一些。

### Q68 ★ 大 PR 怎么控制成本和上下文？

> **答**：每批 3–5 个文件，批次并发 1–4（默认 2），文件数/Diff 行数有上限；单批失败隔离，不影响其他批；批次进度 50–89；取消在批边界检查。187 文件实测：并发 2、46 批、184 analyzed、3 skipped、60.1 秒；串行版本 137.6 秒。

### Q69 ★ 为什么默认用 v4.1 Flash，不用 Pro？

> **答**：D02 用 5 个受控案例对比：两者结构化/schema/核心缺陷都是 5/5；Flash 平均 6.0 秒、7,229 tokens，Pro 10.6 秒、7,916 tokens。Flash 平均延迟低约 43%，更适合异步主链路；Pro 保留给复杂/高价值 PR，通过 `pr.ai.deepseek.model` 一行切换。

### Q70 ★ Token 成本和调用次数大概多少？

> **答**：README 真实样例单任务 20.8 秒、3 次调用（1 次总结 + 2 次问题）、4,504 tokens。成本随文件数和批次数增长；我们通过批大小、并发、文件/Diff 上限和模型选择控制。没有伪造单价，只用 token 作为成本代理。

### Q71 ★ 模型超时或某一批失败怎么办？

> **答**：单批失败只标记该批文件失败，其他批和已入库结果保留；任务最终是部分完成或失败；模型超时映射错误码 6，格式错误映射 7。不会用一批失败覆盖整个任务，也不会无限重试。

### Q72 ★ PR 里的恶意注释会不会攻击 Prompt？

> **答**：我们把 PR 文本和代码当不可信输入：系统提示明确要求忽略代码/注释里的指令；工具只读、路径白名单、无 shell/任意网络；模型输出还要经过文件/行号/字段校验。它能降低风险，但不能证明模型完全免疫 prompt injection，这是 LLM 应用的共性边界。

### Q73 ★ 为什么不做 RAG/微调/仓库级索引？

> **答**：当前先保证单 PR 闭环和输出可信，RAG/符号索引属于加分项 X02，成本和工期都更高。现在的 `find_callers`/`read_tests` 是轻量只读工具，已能补一部分跨文件上下文；真实跨文件 ground truth 样本还不够，这是我们下一步要补的。

### Q74 ★ 你们的问题有效率只有 50%，怎么解释？

> **答**：这是严格口径：1 条拼写缺陷算有效，1 条“个人练习叙述”属于主观建议，算无效，所以 1/2=50%；宽松口径 2/2。已知缺陷检出率是 2/2，行号 1/1。样本只有 1 个真实 PR，不能外推整体准确率；我们在文档里明确写了样本限制，下一步补 3–5 个带人工标注的公开 PR。

### Q75 ★ 典型误报和漏报是什么？

> **答**：误报主要是范围/风格建议，比如“缺少项目说明”，没有可验证的代码证据；控制手段是 low 严重度、待确认、证据为空降置信度、人工可标误报。漏报方面，当前样例没有已知缺陷漏报，但跨文件真实样本不足，不能宣称复杂逻辑漏报率低。

### Q76 ★ 报告和问题是怎么入库、怎么导出的？

> **答**：第一阶段写 `analysis_report`（purpose/changes/impacts）；第二阶段问题校验后写 `review_issue`，保留 `ai_suggestion` 和可编辑的 `suggestion`；导出时按任务 `report_language` 生成 Markdown，包含 PR 信息、版本、总结、问题、人工处理结论和未覆盖范围。

## 8. 安全与权限

### Q77 ★ 为什么用 Sa-Token opaque token，不用 JWT？

> **答**：JWT 撤销和刷新旋转要额外维护黑名单；我们用 Redis 保存 access-token 会话和 refresh-token，退出/刷新/封禁可以立即失效。opaque token 不携带用户信息，每次查 Redis，换来可控的撤销能力。

### Q78 ★ refresh-token 怎么旋转？旧 token 为什么失效？

> **答**：刷新时先校验 Redis 里的 refresh-token，再删除旧 token 和用户集合里的记录，签发新 access + refresh；旧 refresh 再用返回 401。退出时注销当前 access-token，并删除该用户全部 refresh-token。注意：其他设备已签发的 access-token 最多还能用到 30 分钟过期，若要立即全端下线需要按 loginId 强制注销。

### Q79 ★ 登录失败限制怎么做的？

> **答**：按用户名计数，连续失败 5 次锁定 15 分钟；用户名不存在和密码错误统一提示，避免枚举账号。计数存 Redis，登录成功清零。

### Q80 ★ 如何防止横向越权？

> **答**：`TaskAccessService` 统一校验：登录用户必须是任务所有者，或持有匹配且未过期的 guestToken；删除/对比/设置只允许本人或对应角色；所有任务子资源（文件、问题、报告、导出）先校验任务归属，再按 fileId/issueId 查询，避免只按子资源 ID 越权。Controller 不自行判断归属。

### Q81 ★ 游客 token 安全吗？

> **答**：token 是 32 字节随机数的 64 位 hex，任务级绑定，默认 7 天过期；只能访问该任务及子资源，不能列表/删除/设置/对比；错误 token 不能枚举任务。分享链接和导出会用 `guestToken` 查询参数，存在被日志/Referer 泄露的风险；我们访问日志不记录 query，生产必须走 HTTPS，敏感场景可以改成一次性兑换或短 TTL。
>
> **边界**：过期只影响访问，当前没有自动清理数据。

### Q82 ★ 限流怎么做的？

> **答**：Redis 计数器：PR 预览 30 次/分钟/IP，游客创建任务 5 次/小时/IP；超过返回 429。Redis 不可用时放行，避免限流组件拖垮主链路。当前 key 用 `remoteAddr`，生产在 Nginx/网关后面要信任代理头或把限流上移到网关，这是已知改进点。

### Q83 ★ 输入校验、SQL 注入、XSS 怎么防？

> **答**：DTO 用 Jakarta Validation 校验必填/长度/格式；PR URL 用专用解析器，只接受 GitHub PR 格式；分页、枚举、忽略目录都有范围/路径校验；MyBatis 使用参数绑定，不拼接用户输入；Vue 默认转义，前端没有 `v-html`，Markdown 导出是文本文件不是 HTML。未知异常统一返回通用提示，不把 SQL/堆栈给客户端。

### Q84 ★ 敏感信息怎么保护？

> **答**：真实密钥只在本地配置/环境变量/`.env`，仓库只有示例；日志布局统一脱敏，访问日志不记录 query/请求体/请求头；模型日志只记录 token 和耗时，不记录 prompt/代码；Docker 镜像非 root，MySQL/Redis 不映射宿主机端口，Nginx 加安全响应头。生产还要改默认密码、接 TLS 和密钥管理。

### Q85 ★ CORS 和 CSRF 怎么处理？

> **答**：开发期 CORS 只允许 `localhost`/`127.0.0.1` 的源，允许凭证；生产要收窄到实际域名。认证走 `Authorization` 头，不读 Cookie，所以传统 CSRF 面很小；但 CORS 配置错误仍可能放大风险，部署时要按域名收紧。

### Q86 ★ 管理员权限怎么控制？

> **答**：管理员接口用角色注解/权限校验，只有 `ADMIN` 可访问；普通用户只能操作自己的任务；管理员也不能删除当前登录用户。前端隐藏按钮只是体验，不作为权限依据。

### Q97 ★ 中期要求的页面原型覆盖了吗？

### Q100 ★ 主题和双语怎么做的？

### Q101 ★ 响应式适配做了吗？

> **答**：中期要求 PC + 移动端布局合理；当前联调页优先保证桌面联调，响应式细节和移动端 Diff 浏览还在完善。答辩时如实说“前端适配进行中”，不把未验证的说成已完成。

### Q102 ★ 前端是正式交付吗？

> **答**：不是。`frontend/` 是临时联调页，已被 `.gitignore` 排除；正式前端七类页面、主题/双语、响应式和设计稿仍在开发。后端接口和状态机已经稳定，前端可以按接口文档并行推进。

### Q103 ★ 前后端接口契约怎么确认的？

> **答**：统一 `/api` 前缀、`{code,message,data}`、分页 `PageResult`；接口文档列出认证、PR、任务、文件、问题、报告、设置、管理员接口；前端 `api.js` 集中封装，错误按 `code` 处理；枚举和状态码在 `docs/数据与状态变更.md` 对齐。

### Q104 ★ 前端没完成，中期答辩怎么讲？

## 12. 压力与刁钻问题

### Q118 ★ 你们的创新点是什么？

> **答**：不是模型本身，而是工程闭环：任务固定版本、两阶段分析、文件/行号/证据校验、部分完成语义、游客任务级分享、人工反馈和版本对比。把“不可信的模型输出”变成可复核的结果，这是我们主要的设计价值。

### Q119 ★ 这是不是套壳 ChatGPT？

> **答**：不是。模型只是其中一层；我们做了 GitHub 接入、异步任务状态机、上下文构建、只读工具循环、结构化 schema、行号/证据校验、去重、权限、幂等、限流、报告和反馈。直接用聊天窗口无法保证版本一致、行号正确和结果可追溯。

### Q120 ★ AI 分析结果敢直接用于生产 Review 吗？

> **答**：不把它当“已确认缺陷”。严重度和置信度分开，证据不足标待确认，人工可以标误报；我们的定位是辅助评审，帮助优先看哪些文件和风险，而不是替代 reviewer。真实样本也证明有主观误报，所以必须保留人工环节。

### Q121 ★ 成本会不会很高？

> **答**：单 README PR 约 4,504 tokens、20.8 秒；大 PR 通过批次、并发和文件/Diff 上限控制。默认用 Flash 而不是 Pro，就是延迟和成本取舍。没有虚构金额，实际成本取决于 provider 单价；后续可以用反馈数据决定哪些 PR 值得用 Pro。

### Q122 ★ 代码和 PR 数据隐私怎么保证？

> **答**：只处理公开 PR；Token/Key 只在服务端；日志不记录 prompt、完整代码和令牌；模型调用会把代码片段发送到配置的 provider，这一点在产品说明里要明确告知。私有仓库和更严格的数据隔离是后续范围。

### Q123 ★ 最大的技术难点是什么？

> **答**：三个：一是模型输出的可信化（文件/行号/证据/去重）；二是异步任务的状态一致性和部分完成语义（claim、取消、重启恢复）；三是大 PR 的上下文和成本控制（批次、并发、上限、失败隔离）。UI 的 Diff 联动是前端难点。

### Q124 ★ 如果重做，会改什么？

> **答**：把创建任务后的投递改成事务提交后按 taskId 触发、定时扫描兜底；把 GitHub 调用移出数据库事务；补问题反馈历史表；加游客同版本去重；做真实跨文件评测集；前端正式化。

### Q125 ★ 为什么不用现成的开源方案？

> **答**：现成方案要么偏静态规则、要么偏通用聊天，难以满足课程要求里的版本一致、结构化校验、部分完成和自定义反馈；我们自己实现能讲清每一层取舍。不是宣称比开源强，而是按需求做可控的闭环。

### Q126 ★ 项目能按时做完吗？

> **答**：后端主链路已完成并有回归；剩余是前端正式页面、部署复验和评测补充。按当前进度可控，但前端和 Docker 目标机验证是风险点，我们已在计划里单独列出，不用“后端完成”掩盖。

### Q127 ★ 用户量上来怎么办？

> **答**：先把 dispatcher 换成 MQ/任务分片，worker 水平扩展；claim 已经保证多实例不重复执行；数据库按任务/时间归档；patch 移对象存储；限流上移网关；AI 批次并发按 provider 限额调整。当前单体架构不是永久方案。

### Q128 ★ 如果 GitHub 限流或模型服务故障，用户看到什么？

> **答**：任务进入失败/部分完成，带明确错误码和重试入口；GitHub 限流映射 2、权限 3、失败/超时 4；模型超时 6、格式错误 7；前端展示原因，不会一直转圈。已生成的报告/问题不会被清空。

### Q129 ★ 怎么保证多个用户同时操作不出错？

> **答**：任务归属校验；状态更新用条件 UPDATE；创建用幂等键；问题入库串行化去重；反馈是最后写入者生效（没有乐观锁），极端并发下可能覆盖，这是已知边界；任务级操作不会互相污染。

## 13. 现场演示追问

### Q130 ★ 现场演示路线是什么？

> **答**：登录 demo → 输入 `octocat/Hello-World#11596` 预览 → 创建任务 → 轮询 1→2→3 → 打开报告/覆盖范围/重点文件 → 文件 Diff → 问题详情/反馈/撤销 → 导出 Markdown；再展示一个部分完成或过期场景；网络失败切 fake 预创建任务。

### Q131 ★ 为什么这个 PR 只有 2 条 low 问题？

> **答**：它只改了 README，真实缺陷是两处拼写，模型合并成一条 low 问题；另一条是主观建议。我们没有为了“好看”伪造高危问题；这正好说明严重度和置信度是分开的，低风险 PR 不应硬报高危。

### Q132 ★ 进度为什么跳变/不是平滑的？

> **答**：阶段进度是离散的（5/10/20/35/50/90/100），AI 批次在 50–89 之间按完成批次递增；轮询 2 秒一次，所以看起来会跳。状态和阶段来自数据库，不是前端假动画。

### Q133 ★ 怎么证明行号是对的？

> **答**：任务固定 head SHA，`PatchLineIndex` 解析新文件侧新增行，问题只允许落在这些行；现场点问题能定位到 Diff 对应行，GitHub 链接也指向同一 SHA。删除文件/无新增行的问题会降级为报告级，不伪造行号。

### Q134 ★ 这些数据是不是提前造的？

> **答**：真实模型样例来自公开 PR 实际调用，日志记录了耗时和 token；fake provider 的用例在文档里明确标注为 fake，只验证状态机/校验，不冒充真实效果。任务 ID、时间、GitHub 链接都可以现场核对。

### Q135 ★ 演示失败了怎么办？

> **答**：准备三层兜底：预创建的完成/部分完成任务、fake provider、截图/录屏；先讲设计再看实时链路。不现场安装依赖、不现场等大 PR 分析；如果网络/模型失败，直接展示错误码和重试入口，这也是功能的一部分。

### Q136 ★ 评委现场加一个需求怎么办？

> **答**：先判断属于哪一类：如果是设置项/展示字段，可以说明改动点和影响范围；如果涉及数据模型或外部集成，按“需求编号 → 设计 → 接口 → 测试”的流程评估，不现场承诺无法验证的功能。中期答辩重点是设计能力，能把边界和代价讲清楚比硬接需求更重要。
