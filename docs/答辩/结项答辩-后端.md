# 结项答辩 · 后端部分

> 建议时长 12–15 分钟；后端 8–9 分钟，演示 3–4 分钟，问答 3 分钟。
> 结项考察重点：完成度、架构思想、关键模块/难点、测试结果、已知问题与改进方向。

## 幻灯片结构

### 1. 封面

- AI PR Review 助手平台
- 后端实现与质量验证
- 姓名/组号/日期

**讲稿**：
> 我汇报后端部分：架构、数据与状态、两阶段 AI 分析、非平凡设计、测试指标和交付边界。

### 2. 问题与范围

- 目标：把公开 GitHub PR 变成可追溯的评审报告
- 输入：PR URL
- 输出：分层总结、重点文件、候选问题、证据、建议、Diff 定位、可导出报告
- 角色：游客/登录用户/管理员
- 不做：私有 PR/私有仓库访问、自动发布 GitHub 评论、增量分析
- 已做：GitHub OAuth 登录/账号绑定、用户级 GitHub Token、管理员 OpenAI/Anthropic 模型配置、用户偏好模型（OAuth scope 仍按公开 PR 最小化）

**讲稿**：
> 我们优先保证“真实 PR、真实分析、可追溯”，而不是做一个只能演示静态数据的页面。

### 3. 系统架构

```text
React 19 前端（已交付）
        │ /api
      Nginx（部署时）
        │
Spring Boot 后端
  controller → service → mapper → MySQL
        │            │
        │            └─ Redis（token/幂等/限流/缓存）
        ├─ GitHub REST API（PR/文件/内容）
        ├─ GitHub OAuth（登录/绑定，用户 token 加密保存）
        ├─ OpenAI Chat Completions / Anthropic Messages（管理员配置）
        └─ task worker（异步状态机）
```

- 后端单 Maven 模块，按职责分包：`controller/service/task/core.analysis/core.agent/core.github/mapper`
- 支撑包：`common.*`（exception/result/properties/util/logging/interceptor/cache/crypto）与 `config`
- 身份/模型扩展：`core.github.oauth`、`service.GitHubTokenProvider`、`core.agent.ai.ModelClientRouter`
- 详细图见 `docs/答辩/后端架构与数据图.md`

**讲稿**：
> 我们没有为了“看起来分层”拆多模块；单模块内按职责分包，AI 和任务引擎独立于普通 CRUD service。

### 4. 数据模型与状态机

- 9 张表：用户、GitHub 绑定、模型配置、设置、PR、任务、文件、报告、问题
- 报告/问题/行号都绑定任务固定 `head_sha`
- 任务状态：1 排队、2 分析中、3 完成、4 部分完成、5 失败、6 取消
- 失败码：1–11 区分 PR、GitHub、Diff、模型、用户 token 失效、公用 token 无效
- 取消/完成都用条件更新；启动时 2→5/8

**讲稿**：
> 数据模型的核心是“任务即版本”：同一任务下的总结、问题和行号来自同一提交，PR 更新只让旧报告过期，不覆盖历史。

### 5. 异步任务与可用性

- 固定 2 worker + 有界队列；DB 状态持久化
- 创建任务立即返回；前端 2 秒轮询 `/progress`
- 取消在阶段边界生效；重试只允许 4/5/6
- 启动恢复：排队任务重投，运行中任务标记失败
- GitHub/模型超时、429/5xx 退避、错误码映射
- 阶段/耗时/失败阶段写结构化日志

**讲稿**：
> 这里解决了“页面刷新/服务重启/取消”三个容易丢状态的问题；状态不在内存里，全部落库。

### 6. 两阶段 AI Agent

```text
阶段 1：PR 总结 + 重点文件（submit_summary）
阶段 2：每批 3–5 文件 → 工具补上下文 → submit_issues
```

- 工具：`read_file`、`find_callers`、`read_tests`，只读、限大小、无 shell
- 每批最多 6 轮模型调用/8 次工具调用
- 未调用提交工具先提醒一次，仍失败该批失败
- 两阶段避免“一边总结一边找问题”的上下文混乱
- 模型客户端抽象：`ModelClientRouter` 路由 OpenAI Chat Completions / Anthropic Messages / fake
- 管理员模型配置是唯一入口；任务写 `model_config_id` + `analysis_config.model` 快照
- 环境兜底仍保留 `pr.ai.provider=deepseek/fake`；数据库模型优先

**讲稿**：
> 不使用自由文本解析，而是让模型调用结构化提交工具；后端再做字段、文件、行号和证据校验。

### 7. 上下文、校验与降噪

- GitHub Contents API 固定 head SHA；单文件 20KB；TS/Python 函数级提取
- patch 行号索引：只接受新文件侧新增行
- 证据为空 → 置信度 ≤60；无法定位 → 降级报告级
- 去重：文件 + 类别 + 规范化标题
- 同根因合并；纯风格不生成高危
- 并发批次入库串行化，避免重复问题

**讲稿**：
> 模型可能编造文件和行号，所以后端是最终裁判；不可定位的问题宁可降级/丢弃，也不伪装成行内缺陷。

### 8. 结构化 Diff 与版本对比

- F20：`GET /tasks/{id}/files/{fileId}/diff`
  - `rows`（hunk/add/delete/context）、新旧行号
  - `addedLines/hunkLines`、问题 `issueIds/highestSeverity`
- F22：同 PR 两版本
  - 路径（含重命名）+ 类别 + 标题匹配
  - added/remaining/resolved、`lineShifted`、`matchConfidence=low`
- 不新增表，不重复计算增量

**讲稿**：
> 前端不再自己解析 patch；后端直接给结构化行和问题标记。版本对比把“行号偏移”和“低置信匹配”显式暴露给用户。

### 8.1 GitHub 身份、用户 Token 与模型配置

- GitHub OAuth：state 一次性校验 + 前端 ticket 兑换原 Sa-Token 双 token；回调不把 GitHub token 放进 URL
- `user_github_binding` 一对一：GitHub 数字 id 唯一，login/avatar/email 只展示；token AES-GCM 加密，支持失效/撤销
- Token 选择：已绑定用户 token → 公用 token → 无 token；用户 token 401 不回退，接口 403 + `githubAuthRequired`，任务 `errorCode=10`
- 模型配置：管理员维护 OpenAI Chat Completions / Anthropic Messages；API Key 加密、列表只返回末 4 位掩码；base URL 做 HTTPS/公网/重定向校验
- 用户偏好：只能选 enabled 模型；管理员停用后保留偏好但 `effectiveModel` 回退默认/环境
- 任务快照：`model_config_id` + `analysis_config.model`，历史报告不随配置改名/停用变化
- 顺手修复受保护接口 OPTIONS 预检被 Sa-Token 拦截成 500 的 CORS 问题

**讲稿**：
> 这一轮把 GitHub 从“服务端一份公用 token”升级为“身份 + 用户 token + 降级链”，并把模型从环境写死升级为管理员配置；所有 token/Key 都加密落库，任务保存模型快照，历史结果不会被后续配置改动污染。

### 9. 安全与数据保护

- Sa-Token opaque access-token 30 分钟；Redis refresh-token 7 天，旋转/撤销
- BCrypt 密码；登录失败按用户名限流
- 任务归属统一校验；游客任务级 token；过期 403
- 用户设置不返回模型 Key；日志脱敏
- GitHub token / 模型 API Key 只存 AES-GCM 密文，密钥来自 `PR_SECURITY_ENCRYPTION_KEY`；接口只返回掩码或绑定状态
- OAuth state/ticket 一次性、短 TTL；GitHub token 不进 URL/前端/日志
- CORS 预检由最高优先级 CorsFilter 处理，避免 OPTIONS 被登录拦截器误判
- 请求 traceId、访问日志、滚动文件、独立 ERROR 日志
- 创建/重试幂等键，Redis TTL 10 分钟

**讲稿**：
> 安全不是只靠前端隐藏按钮；Controller/Service 都会校验归属。日志里也不出现 Key、Token 或完整代码。

### 11. 模型选择与并发取舍

- D02：5 个受控案例，两者结构化/schema/核心缺陷均 5/5
- Flash 平均 6.0s，Pro 10.6s；Flash token 少约 8.7%
- 默认 Flash；Pro 作为复杂/高价值 PR 可选
- 管理员可在 `ai_model_config` 覆盖默认；环境兜底仍是 `pr.ai.provider=deepseek/fake`
- D03：批内并发默认 2，范围 1–4；单批失败隔离
- 大 PR 串行 137.6s → 并发 60.1s
- 不盲目提高并发，避免模型限流和内存峰值

**讲稿**：
> 模型选择不是“越大越好”；在结构化稳定性和核心缺陷检出相同的前提下，Flash 的延迟和 token 更适合主链路。

### 12. 部署与交付

- Dockerfile：JDK 17 多阶段、非 root
- Compose：MySQL 8.4、Redis 7.4、Backend、Nginx
- Nginx：`/api` 反代、SPA 回退、安全响应头、`X-Request-Id`
- `.env.example` 仅占位符；本地配置/日志/target 排除
- 数据库 schema、迁移脚本、接口文档、测试/设计文档齐全
- **边界**：当前机器无 Docker，容器构建和 `nginx -t` 需目标机复验

**讲稿**：
> 交付材料按“可复现”准备；没有把未验证的容器构建说成已完成，现场会如实说明目标机复验项。
