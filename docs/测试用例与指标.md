## 1. 结论摘要

- 20 个用例全部执行，20/20 符合预期。
- 真实模型在已知缺陷样例上完成总结、问题提取、行号定位和报告落库，单任务耗时 20.8 秒，3 次模型调用，共 4504 tokens。
- 已知 2 处拼写缺陷全部检出，缺陷级检出率 100%；报告问题行号定位 1/1 正确。
- 问题有效率按严格口径为 50%（1 条拼写问题 + 1 条主观建议）；按宽松口径为 100%。典型误报是“个人练习叙述”这类主观范围建议。
- 本样例没有已知缺陷漏报；但样本只有两处拼写，不能代表复杂逻辑或跨文件缺陷的漏报水平。
- 大 Diff 用例使用 187 文件的公开 PR，系统完成 156 个文件分析、3 个文件跳过，任务按部分完成结束，没有 OOM 或无限等待。
- 模型超时、部分完成、启动恢复、非法输出都能落到明确状态和错误码，未出现“运行中永久卡住”。

## 5. 误报与漏报分析

### 典型误报

1. **“个人练习叙述，缺少项目相关说明”**：属于范围/风格建议，不是客观缺陷。当前以 low 严重度、待确认状态输出，人工可忽略；后续 prompt 可要求“必须给出可验证的代码或文档证据”，减少主观评价。
2. **伪造/无法定位的问题**：由模型直接给出不存在的文件或行号时，校验会丢弃；若整批都无效，任务标记部分完成，不会把错误问题写进报告。

### 典型漏报

1. **本样例没有已知缺陷漏报**：`Softwarw` 和 `fir` 都被覆盖；模型把两处拼写合并为一条问题，因此缺陷级检出 2/2，问题级只算 1 条有效问题。
2. **跨文件真实缺陷样本不足**：当前跨文件路径有单测和 fake 用例，但缺少带人工标注的真实跨文件 PR；下一轮应补 3–5 个有已知跨文件缺陷的公开 PR，才能评估复杂漏报。

### 控制手段

- 行号必须命中 patch 新增行；文件必须属于当前任务；无法定位则丢弃或降级报告级。
- 证据为空时置信度上限 60，并保持待确认。
- 同文件 + 类别 + 规范化标题去重。
- 批次失败/非法输出不覆盖已完成结果，任务以部分完成返回。
- 真实 Key 不落库、不写日志；日志只记录 token 数量、耗时和状态。

## 6. 复现方式

### 真实模型

```powershell
cd backend
.\mvnw.cmd -q -DskipTests package
java -jar target\backend-0.0.1-SNAPSHOT.jar --server.port=18080
```

在 `application-dev.yml` 配置 `pr.ai.deepseek.base-url`、`api-key`、`model`（本机验证模型 `deepseek/deepseek-v4.1-flash`），然后通过 `/api/tasks` 创建 `https://github.com/octocat/Hello-World/pull/11596` 任务并轮询进度。

### 无 Key 联调

```powershell
java -jar target\backend-0.0.1-SNAPSHOT.jar --server.port=18080 --pr.ai.provider=fake
```

fake 用例用于验证状态机、工具循环、校验、部分完成和版本对比，不代表真实模型质量。

### 大 Diff

使用 `vercel/next.js#100042`，建议配置服务端 GitHub Token 以提高 API 限额；无 Token 时未认证限流为 60 次/小时。
