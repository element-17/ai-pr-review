## 十月项目实施与答辩要求

十月项目周期为三周，期间设置中期答辩和结项答辩。各项目组应结合项目规模合理安排开发进度，在规定时间内完成设计、开发、测试与成果展示。

## 一、答辩要求

**中期答辩**重点考察需求分析、数据库设计和 UI 设计。项目组应提交需求说明、主要业务流程、数据库概念及逻辑设计、页面原型，并展示项目任务拆解与当前开发进度。对于涉及第三方服务的项目，应说明接口接入方案及已完成的验证工作。

**结项答辩**重点考察项目完成度及架构设计思想。项目组应现场演示核心业务流程，说明前后端架构、关键模块、数据库设计、技术选型及主要实现难点，并展示测试结果、已知问题和后续改进方向。

## 二、项目过程要求

1. 迭代管理：须使用云效平台进行需求拆解、任务分配和进度跟踪，完成至少两次迭代。需求、开发任务和缺陷应明确负责人、所属迭代及完成状态，并及时更新；需要集中调整时可使用批量更新功能。答辩时应能够展示迭代计划与任务完成情况。

2. 版本管理：须使用 Git 管理代码。完成相对独立的功能、修复或调整后，应及时提交，并使用能够说明变更内容的提交信息。不得在项目结束时将全部代码作为单次提交上传。

3. 响应式设计：Web 项目的前端页面须适配 PC 端和移动端。导航、表单、列表及核心操作区域应在不同屏幕宽度下保持布局合理、内容可读、操作可用。

4. AI 辅助开发：允许使用 Codex、Cursor 等工具辅助开发。项目成员须理解并能够解释所提交的代码及关键设计决策；AI 生成的内容应经过检查、运行和必要的修改，不得以工具生成结果代替测试与答辩说明。

5. 基本质量要求：项目应对无效输入、接口失败等常见异常给出明确反馈；访问密钥等敏感配置不得提交至代码仓库。核心业务流程须经过实际测试，不得仅以静态页面或演示数据代替已要求实现的功能。

6. 交付材料：结项时须提交项目源码、运行说明、数据库初始化文件、主要接口说明、系统架构图及核心功能测试记录，确保项目具备基本的复现与验收条件。

项目组可根据完成情况实现扩展功能，但应优先保证核心流程完整、真实可用。

## 三、理想进度

| 时间    | 主要目标                                      |
| ----- | ----------------------------------------- |
| 第 1 周 | 完成需求、数据库和 UI 设计；跑通“输入 PR → 获取真实变更”；准备中期答辩 |
| 第 2 周 | 完成 AI 分析、报告展示、Diff 定位和反馈，形成可演示的完整流程       |
| 第 3 周 | 完成账户与历史、主题与双语言、响应式适配；集中联调、修复和准备结项答辩       |

## 四、前端开发要求（全栈无需关注）

1. 技术框架：使用 Vue 3 或 React 开发，不得仅使用静态页面完成项目。建议结合团队已有经验选择框架，并在项目内保持技术方案统一。

2. 组件库：允许使用成熟的 UI 组件库。Vue 3 项目推荐 Element Plus，也可使用 Ant Design Vue；React 项目可使用 Ant Design。使用组件库时应统一页面风格，避免同类组件样式混乱。

3. 接口协作：前端与后端应尽早确认接口地址、请求参数、返回结构及异常状态。接口调用应集中封装，避免在页面组件中重复编写请求和错误处理逻辑。

4. 页面状态：核心页面应完整处理加载中、无数据、请求失败和操作成功等状态。对于耗时较长的操作，应展示进度或明确的等待提示，避免用户重复提交。

5. 响应式适配：按照项目总体要求完成 PC 端和移动端适配，并实际检查主要页面的布局及核心操作。表格、代码展示等宽内容应提供适合移动端的浏览方式。

6. 代码质量：合理划分页面、组件与公共逻辑；使用清晰的命名和必要的类型定义。提交前应检查项目能否正常构建，避免遗留明显报错、无效代码或仅供调试的内容。

主题切换、双语言等功能已列入具体项目需求，应在页面开发时同步考虑，并检查正常、空数据及错误状态下的显示效果。

## 四、后端开发要求

1.**技术栈要求**

- 后端必须基于 **Java + Spring Boot + MyBatis-Plus** 实现。
- 统一使用 RESTful 接口风格，接口路径、请求方式、响应格式需保持一致。
- 使用 **分层架构**：Controller、Service、Mapper、Entity/DTO/VO 分离，避免在 Controller 中写业务逻辑或直接拼接 SQL。

2.**MyBatis-Plus 使用要求**

- 优先使用 MyBatis-Plus 的条件构造器、分页插件和公共字段能力，减少重复 SQL 与手写 Mapper。
- 对通用增删改查应尽量通过 Service 封装；复杂查询可编写 Mapper XML，但需保证命名规范、参数清晰、可维护。
- 需合理设计实体类字段、表映射、逻辑删除、自动填充（如创建时间、更新时间）等

3.**接口设计规范**

- 所有接口应统一返回结构，例如：
  - `code`：状态码
  - `message`：提示信息
  - `data`：业务数据
- 接口需区分成功、失败、参数错误、权限不足等场景。
- 对关键业务接口需支持幂等处理，避免重复提交造成数据异常。

4.**安全性要求**

- **认证与授权**：引入统一登录认证机制，禁止“所有接口裸奔”，采用 Sa-token等方式进行访问控制。
- **权限控制**：按角色/权限做细粒度控制，敏感接口必须校验权限，不能仅依赖前端隐藏按钮。
- **输入校验**：对请求参数进行严格校验，包括必填、格式、长度、取值范围、特殊字符过滤，防止 SQL 注入、XSS、参数篡改等风险。
- **密码安全**：用户密码必须加密存储，禁止明文保存，并限制登录失败次数。
- **敏感信息保护**：日志、异常返回、接口响应中不得输出密码、密钥、Token、身份证、手机号等敏感数据。
- **防越权访问**：对“查看/修改他人数据”类接口，必须校验当前用户与资源归属关系，防止横向越权。
- **接口防护**：对高风险接口增加防重放、限流等措施。
- **错误处理**：统一异常处理机制，禁止直接把堆栈、SQL、数据库错误信息返回给客户端。

5.**代码与工程质量**

- 需遵守命名规范，包结构清晰，代码注释适度。
- 应输出接口文档，便于前后端联调与答辩展示。
- 数据库表结构需提交建表脚本，并说明字段含义、索引设计、外键关系、逻辑删除策略。
