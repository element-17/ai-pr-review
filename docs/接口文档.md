### 当前实现补充（2026-10-30）

为避免早期契约误导联调，先列出当前实现的关键差异和缺失的接口章节：

- 成功码统一为 `200`；错误码为 HTTP-like 业务码 `400/401/403/404/409/429/5xx`。下文 §1.1/§1.8 中的 `code:0`、`40001/40901/51001` 是早期契约，仅保留作历史参考。
- 分页统一返回 `PageResult{total, records}`；下文 §1.1 的 `data.list/page/pageSize` 是早期契约。

- 刷新令牌接口为 `POST /api/auth/refresh`，请求体 `{"refreshToken":"..."}`，返回与登录相同的 `LoginVO`（accessToken、refreshToken、tokenType、expiresIn、userInfo），旧 refresh-token 立即失效。
- 管理员接口需要 `ADMIN` 角色，统一前缀 `/api/users`：

| 方法 | 路径 | 说明 |

| PUT | `/api/users/{id}` | 更新用户 |

| PUT | `/api/users/{id}/status` | 启用/禁用 |

完整请求/响应示例以 Swagger `/v3/api-docs` 和 `backend/README.md` 为准；下文未列出的历史示例不再作为联调依据。

## 1. 通用约定

### 1.1 响应结构

除 Markdown 导出外，所有接口都返回同一个信封：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

- `code`：业务码，`0` 表示成功，非 `0` 见 1.8。
- `message`：给人看的提示，不包含堆栈、SQL、令牌或完整代码。前端展示优先使用自己的 i18n 文案，`code` 用于判断分支。
- `data`：成功时是对象或数组；失败时可以是 `null`，也可以带定位信息，例如 `{"field":"url"}`。
- 列表统一放在 `data.list`，分页字段放在 `data.total`、`data.page`、`data.pageSize`。
- 空数组返回 `[]`，不返回 `null`；单个对象确实不存在时返回 `null` 或对应错误码。

错误响应示例：

```json
{
  "code": 40901,
  "message": "相同提交版本的任务正在执行",
  "data": {
    "existingTaskId": 123
  }
}
```

### 1.2 HTTP 状态码

业务码和 HTTP 状态码同时使用，前端先看 HTTP 状态，再看 `code`。

| HTTP | 使用场景 |
| --- | --- |
| 200 | 查询、更新、取消、删除成功 |
| 201 | 注册成功 |
| 202 | 任务创建、重试、取消请求已受理 |
| 400 | 参数格式错误、缺少必填项、枚举越界 |
| 401 | 未登录、令牌过期、账号密码错误 |
| 403 | 无权访问、游客令牌无效或过期 |
| 404 | 资源不存在、报告未生成 |
| 409 | 任务状态冲突、重复运行、邮箱已注册 |
| 429 | 登录锁定、请求限流、GitHub 限流 |
| 500 | 服务端内部错误 |
| 502 | GitHub 请求失败 |
| 504 | GitHub 请求超时 |

不使用 `204`。删除接口返回 `200`，`data` 里带删除结果，前端处理更统一。

### 1.3 字段、时间和 ID

- JSON 字段使用 camelCase，数据库列使用 snake_case，MyBatis 开启 `map-underscore-to-camel-case`。
- 时间统一 `yyyy-MM-dd HH:mm:ss`，时区 `Asia/Shanghai`。请求里的日期筛选使用 `yyyy-MM-dd`。
- ID 当前是自增 `BIGINT`，JSON 中按 number 返回。以后如果改雪花 ID，再统一改成 string 并同步前端。
- 状态、阶段、类型都返回数字编码，前端通过 i18n 资源转成中文或英文，不在接口里返回固定中文文案。
- 布尔字段用 `true` / `false`，不用 0/1。
- `null` 表示确实没有值，例如报告总结尚未生成、报告级问题没有文件位置。

### 1.4 分页与排序

分页参数：

| 参数 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `page` | int | 1 | 页码，从 1 开始 |
| `pageSize` | int | 见各接口 | 每页条数，超过上限按上限处理 |

分页响应：

```json
{
  "total": 42,
  "page": 1,
  "pageSize": 20,
  "list": []
}
```

`total` 是当前筛选条件下的总条数，不是全表条数。排序字段由各接口单独说明，不提供任意字段排序，避免 SQL 拼接。

### 1.5 认证与权限

#### 登录用户

登录成功后返回 JWT，后续请求带：

```http
Authorization: Bearer <token>
```

- JWT 建议包含 `sub`（用户 ID）、`jti`、`iat`、`exp`，签名密钥使用 `pr.jwt.user-secret-key`。
- 有效期默认 7200 秒，可通过 `pr.jwt.user-ttl` 调整。
- 退出登录时把 `jti` 写入 Redis 黑名单，黑名单 TTL 等于令牌剩余有效期。
- 受保护接口先校验令牌，再在 Service 层校验资源归属，不能只靠前端隐藏按钮。

#### 游客

不登录也可以分析公开 PR。创建任务时不带 `Authorization`，服务端生成游客令牌：

- 游客令牌是 32 字节随机数的 64 位十六进制串。
- 有效期默认 7 天，和任务的 `expire_time` 一致。
- 后续访问任务子资源时带：

```http
X-Guest-Token: <guestToken>
```

- 导出、下载这类直接打开链接的请求，也允许用 `?guestToken=...`。
- 令牌只对创建它的那一条任务有效，不能查历史列表，不能删除任务，不能做版本对比。
- 游客重试会生成一条新任务和新令牌，旧链接在过期前仍可查看。

#### 权限矩阵

| 接口组 | 游客 | 登录用户（本人） | 其他登录用户 |
| --- | --- | --- | --- |
| 注册、登录 | 允许 | 允许 | 允许 |
| 退出、当前用户 | 不允许 | 允许 | 允许 |
| 用户设置 | 不允许 | 允许 | 不允许 |
| PR 预览 | 允许 | 允许 | 允许 |
| 创建任务 | 允许（游客任务） | 允许（本人任务） | 允许（创建自己的任务） |
| 任务列表 | 不允许 | 允许 | 只能看自己的 |
| 任务详情/进度/报告/文件/问题/导出 | 游客令牌 | 允许 | 不允许 |
| 取消、重试、问题反馈、撤销 | 游客令牌 | 允许 | 不允许 |
| 删除任务 | 不允许 | 允许 | 不允许 |
| 版本对比 | 不允许 | 允许（两条任务都属于本人） | 不允许 |

任务访问判定统一为：`user_id = 当前用户` 或 `guest_token = 请求令牌且未过期`。两者都不满足时，返回 `40300`；任务不存在返回 `40401`。

"其他登录用户"一列默认指没有游客令牌的情况。任何人拿到有效游客令牌，都可以按游客列访问对应任务；登录用户打开游客链接时也一样，令牌不因为登录状态而失效。

### 1.6 幂等

- `POST /tasks` 和 `POST /tasks/{taskId}/retry` 支持 `Idempotency-Key` 请求头。
- 服务端把 key、请求体哈希和响应存 Redis，默认 10 分钟。
- 同 key、同请求体重复提交，直接返回第一次的结果。
- 同 key、不同请求体，返回 `40907`。
- 取消、撤销、问题 PATCH 本身是幂等的，重复调用不会产生额外状态。
- 注册接口靠邮箱唯一索引保证幂等，重复注册返回 `40902`。

### 1.7 限流

以下是建议默认值，部署时放配置中心或 `application.yml`：

| 场景 | 限制 |
| --- | --- |
| 登录 | 每 IP 每分钟 10 次；同一账号 15 分钟内失败 5 次锁定 15 分钟 |
| 游客创建任务 | 每 IP 每小时 5 次 |
| PR 预览 | 每 IP 每分钟 30 次 |
| 登录用户普通接口 | 每人每分钟 120 次 |
| GitHub 请求 | 按 GitHub 返回的限流头处理，触发后返回 51002 |

触发限流返回 `429`，并带 `Retry-After` 响应头。GitHub 限流也走 429，但业务码是 `51002`，前端可以提示"稍后再试"。

| 值 | 含义 |
| --- | --- |

### 1.10 异步任务与任务错误码

创建任务只做参数校验、PR 校验和入库，然后返回 `202`。实际拉取 Diff、补充上下文、调用模型由后台线程执行。前端通过 `GET /tasks/{taskId}/progress` 轮询，建议 2 秒一次，状态到 3/4/5/6 后停止。

任务详情里的 `errorCode`：

| 值 | 含义 |
| --- | --- |
| 1 | PR 无效或不存在 |
| 2 | GitHub 限流 |
| 3 | 无仓库权限 |
| 4 | GitHub 请求失败或超时 |
| 5 | Diff 过大 |
| 6 | 模型调用超时 |
| 7 | 模型输出格式错误 |
| 8 | 内部错误 |
| 9 | 任务创建后 PR 又产生新提交，需重新分析 |

`status = 4` 表示有结果但覆盖不完整，例如部分文件被跳过、模型对部分文件失败。`status = 5` 表示没有可用的完整结果。`status = 6` 表示用户取消。失败和取消都会写 `finishTime`，失败/部分完成会尽量写 `errorCode` 和 `errorMessage`。

## 3. 认证接口

### 3.1 注册

**当前已实现的用户名注册契约（对照 `origin/master@6b6ffd1` 的 `RegisterDTO`，2026-10-23 核对）：**

`POST /api/auth/register`，公开；成功返回 `{ "code": 200, "message": "操作成功", "data": null }`，注册后需使用用户名和密码登录。

| 字段 | 必填 | 当前约束 |
| --- | --- | --- |
| `username` | 是 | 3–50 位，仅允许英文字母、数字和下划线，不能空白；是否重复由后端校验。 |
| `password` | 是 | 6–32 位，不能空白或全部为空白字符；当前 DTO 未要求同时包含字母和数字。前端保留密码原值，不自动去掉首尾空格。 |
| `nickname` | 否 | 最多 50 个字符。 |
| `email` | 否 | 有效邮箱格式，最多 100 个字符。 |
| `phone` | 否 | 不填或满足 `^1[3-9][0-9]{9}$`，即以 13–19 开头的 11 位中国大陆手机号。 |

前端对用户名和可选资料去除首尾空白，可选资料留空时省略字段；失焦时显示字段提示，提交前再次校验所有字段。不符合约束时不发起注册请求，并聚焦首个错误字段。后端仍独立校验并判断用户名是否已存在。

**下方邮箱注册、8–64 位密码和注册即返回 JWT 的示例为早期目标契约，当前联调请使用上表。**

`POST /auth/register`，公开。

请求体：

```json
{
  "email": "dev@example.com",
  "password": "Passw0rd!",
  "name": "Asuka"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `email` | string | 是 | 邮箱，最长 255，格式校验 |
| `password` | string | 是 | 8–64 位，至少包含一个字母和一个数字 |
| `name` | string | 否 | 昵称，1–64 位，不填取邮箱前缀 |

响应 `201`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "expiresIn": 7200,
    "user": {
      "id": 1,
      "email": "dev@example.com",
      "name": "Asuka",
      "createTime": "2026-10-21 10:00:00"
    }
  }
}
```

说明：

- 注册成功后直接返回登录令牌，省一次登录请求。
- 同时创建默认 `user_setting` 行：主题跟随系统、中文、检查类别 1–6、默认忽略目录 `node_modules,dist,target,.git`、最大 200 个文件、20000 行 Diff。
- 密码只存 BCrypt 哈希，任何响应都不返回密码字段。

错误：

| code | HTTP | 场景 |
| --- | --- | --- |
| 40001 | 400 | 邮箱格式、密码长度或昵称长度不合法 |
| 40902 | 409 | 邮箱已注册 |

## 5. PR 预览与任务

### 5.1 PR 预览

`POST /prs/preview`，可选 JWT。

用途：F01 的链接校验和基本信息展示。这个接口不落库，只向 GitHub 拉取并返回当前 PR 信息；带 JWT 时额外返回"可复用任务"提示。

请求体：

```json
{
  "url": "https://github.com/octocat/Hello-World/pull/1347"
}
```

URL 只接受：

```text
https://github.com/{owner}/{repo}/pull/{number}
```

允许末尾斜杠、查询参数和锚点，但会被忽略。其他域名、非 HTTPS、缺少 PR 编号都返回 `40002`。

响应 `200`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "pr": {
      "repoFullName": "octocat/Hello-World",
      "prNumber": 1347,
      "title": "Fix authentication edge cases",
      "author": "octocat",
      "state": 1,
      "baseBranch": "master",
      "headBranch": "fix-auth",
      "headSha": "a1b2c3d4e5f60718293a4b5c6d7e8f9012345678",
      "addLines": 120,
      "deleteLines": 30,
      "fileCount": 8
    },
    "reusableTask": {
      "taskId": 123,
      "status": 3,
      "reportLanguage": "zh-CN",
      "createTime": "2026-10-20 15:00:00",
      "finishTime": "2026-10-20 15:02:10"
    }
  }
}
```

说明：

- `reusableTask` 只在带 JWT 时返回；取当前用户在同一 `pr_id + headSha` 下最新的一条已完成或部分完成任务。
- 没有可复用任务时返回 `null`。
- 预览不返回文件列表；文件在任务创建后由后台拉取，通过文件接口查看。
- 私有仓库或无权限统一返回 `51001`，不暴露仓库是否存在。

错误：

| code | HTTP | 场景 |
| --- | --- | --- |
| 40002 | 400 | URL 格式不合法 |
| 40100 | 401 | 带了 Authorization 但令牌无效 |
| 51001 | 404 | PR 不存在、私有仓库或无权访问 |
| 51002 | 429 | GitHub 限流 |
| 51003 | 502 | GitHub 接口失败 |
| 51004 | 504 | GitHub 请求超时 |

### 5.2 创建分析任务

`POST /tasks`，可选 JWT。不带 JWT 创建游客任务，带 JWT 创建本人任务。

请求头（可选）：

```http
Idempotency-Key: 6f1e2d3c-...
```

请求体：

```json
{
  "url": "https://github.com/octocat/Hello-World/pull/1347",
  "reportLanguage": "zh-CN"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `url` | string | 是 | GitHub PR URL |
| `reportLanguage` | string | 否 | `zh-CN` / `en-US`；不填时登录用户取设置里的语言，游客默认 `zh-CN` |

服务端流程：

1. 校验 URL，向 GitHub 拉取 PR 当前元数据。
2. 按 `repo_full_name + pr_number` upsert `pull_request`，更新 `head_sha`、状态和统计。
3. 登录用户检查同一 `user_id + pr_id + head_sha` 是否已有状态为 1/2 的任务；有则返回 `40901`，`data.existingTaskId` 指向已有任务。
4. 生成有效的分析配置快照：登录用户取 `user_setting`，游客用默认值。
5. 写入 `analysis_task`，状态 1、阶段 1、进度 0；游客生成 64 位十六进制令牌和 7 天过期时间。
6. 投递异步任务，立即返回 `202`。

响应 `202`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "taskId": 123,
    "status": 1,
    "stage": 1,
    "progress": 0,
    "reportLanguage": "zh-CN",
    "isGuest": true,
    "guestToken": "2f8c0d7e4b1a9c3d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f708192a3b4c5",
    "expireTime": "2026-10-28 10:00:00",
    "shareUrl": "http://localhost:5173/tasks/123?guestToken=2f8c0d7e4b1a9c3d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f708192a3b4c5",
    "createTime": "2026-10-21 10:00:00"
  }
}
```

登录用户的任务：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "taskId": 124,
    "status": 1,
    "stage": 1,
    "progress": 0,
    "reportLanguage": "zh-CN",
    "isGuest": false,
    "guestToken": null,
    "expireTime": null,
    "shareUrl": null,
    "createTime": "2026-10-21 10:00:00"
  }
}
```

说明：

- 创建接口不接收 `headSha`，以免客户端指定和 PR 当前版本不一致的提交。版本由服务端拉取后固定。
- 创建时同步完成 PR 校验；GitHub 失败会直接返回错误，不会留下排队任务。
- **相同提交版本已有完成结果时，不阻止创建新任务**。前端可以先调预览接口拿到 `reusableTask`，让用户选择查看旧结果还是重新分析。
- 游客令牌只在创建响应里返回一次，前端要保存；服务端不提供找回接口。
- 任务创建后，报告、文件、问题会在后续阶段逐步可查；详情接口会返回当前状态。
- `analysis_config` 当前不通过请求体覆盖，避免前端绕过规模限制。需要改配置时更新用户设置，再创建任务。

错误：

| code | HTTP | 场景 |
| --- | --- | --- |
| 40001 | 400 | 请求体为空、报告语言非法 |
| 40002 | 400 | PR URL 格式错误 |
| 40100 | 401 | 带了 Authorization 但令牌无效 |
| 40901 | 409 | 相同用户、相同版本的任务正在执行 |
| 40907 | 409 | 幂等键对应了不同的请求体 |
| 51001 | 404 | PR 不存在或无权访问 |
| 51002 | 429 | GitHub 限流 |
| 51003 | 502 | GitHub 请求失败 |
| 51004 | 504 | GitHub 请求超时 |
| 42902 | 429 | 游客创建任务过于频繁 |

### 5.6 取消任务

`POST /tasks/{taskId}/cancel`，需要 JWT 或游客令牌。

### 8.3 更新问题处理状态或建议

`PATCH /tasks/{taskId}/issues/{issueId}`，需要 JWT 或游客令牌。

请求体至少包含一个字段：

```json
{
  "feedbackStatus": 2,
  "feedbackRemark": "确认需要修复，已排期",
  "suggestion": "建议在 verifyToken 入口统一处理空 token，并补充 null 和空字符串测试。"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `feedbackStatus` | int | 否 | 1 待确认，2 已采纳，3 已解决，4 误报 |
| `feedbackRemark` | string | 否 | 最长 500；`feedbackStatus=4` 时必填 |
| `suggestion` | string | 否 | 1–5000 字符；空字符串不允许，撤销建议用 undo 接口 |

行为：

- 只更新传入的字段，未传的保持原值。
- 编辑建议只改 `suggestion`，不自动改变处理状态。
- 标记采纳、已解决、误报只改状态和理由，不覆盖模型原文 `aiSuggestion`。
- 误报必须写理由，方便后续统计误报原因。
- 更新是幂等的，同一请求重复提交结果一致。
- 并发编辑采用最后写入生效；响应里的 `updateTime` 可用于前端判断是否过期。

响应 `200`：返回更新后的完整问题详情，结构同 8.2。

错误：

| code | HTTP | 场景 |
| --- | --- | --- |
| 40001 | 400 | 空请求、状态越界、理由超长、建议为空 |
| 40100 | 401 | 未登录且没有游客令牌 |
| 40300 | 403 | 无权访问 |
| 40301 | 403 | 游客令牌无效或过期 |
| 40401 | 404 | 任务或问题不存在 |

### 8.4 撤销人工处理

`POST /tasks/{taskId}/issues/{issueId}/undo`，需要 JWT 或游客令牌。

无请求体。

行为：

- `feedbackStatus` 重置为 1（待确认）。
- `feedbackRemark` 清空。
- `suggestion` 恢复为 `aiSuggestion`。

响应 `200`：返回更新后的问题详情，结构同 8.2。

说明：

- 这个接口撤销的是整条人工处理结果，不只是建议文字。
- 如果只想恢复建议、保留处理状态，前端可以调 PATCH，把 `aiSuggestion` 原文作为 `suggestion` 传回去。
- 重复调用结果一致。

错误同 8.3。

## 9. 典型调用流程

### 9.1 游客分析

```text
POST /prs/preview
  { url }
  -> pr, reusableTask = null

POST /tasks
  { url, reportLanguage }
  -> 202 { taskId, guestToken, expireTime, shareUrl }

GET /tasks/{taskId}/progress
  X-Guest-Token: <token>
  -> status 1/2/3/4/5/6

GET /tasks/{taskId}
GET /tasks/{taskId}/report
GET /tasks/{taskId}/files

  X-Guest-Token: <token>

PATCH /tasks/{taskId}/issues/{issueId}
POST  /tasks/{taskId}/issues/{issueId}/undo
  X-Guest-Token: <token>

GET /tasks/{taskId}/export?guestToken=<token>
```

```text
  -> token

  Authorization: Bearer <token>
  { url }
  -> pr, reusableTask（可能为 null，前端提示查看或重新分析）

  { url, reportLanguage }

  Authorization: Bearer <token>

  Authorization: Bearer <token>
```

```text

  -> 待确认问题，按严重度排序
```

## 11. 实现约定

### 11.1 分层

- Controller 只做参数绑定、校验和调用 Service，不写业务判断和 SQL。
- Service 负责 URL 校验、权限校验、状态流转、GitHub/模型调用编排和事务。
- Mapper 负责单表读写和必要的聚合查询；复杂统计可以写 XML。
- DTO/VO 和 Entity 分离，不直接把数据库实体返回给前端，避免把 `password`、`guest_token`、内部配置带出去。
- 统一 `@RestControllerAdvice` 处理参数异常、业务异常和未知异常，输出 `{code,message,data}`。

### 11.2 权限检查

每个任务子资源请求都按以下顺序检查：

1. 令牌是否有效（JWT 或游客令牌）。
2. 任务是否存在。除删除接口外，任务还必须未逻辑删除；删除接口对本人已删除任务做幂等返回。
3. 当前用户是否为任务所有者，或游客令牌是否匹配且未过期。
4. 子资源（文件、问题）是否属于该任务。

不允许只按 `fileId` 或 `issueId` 查询而不带 `taskId` 条件，避免横向越权。

### 11.3 异步任务

- 任务创建后投递线程池，状态从 1 到 2，再按阶段 2–7 更新。
- 每个阶段结束更新 `stage` 和 `progress`；阶段边界检查任务是否已取消。
- 取消、完成使用条件更新，避免 worker 和用户同时改状态。
- GitHub 请求和模型调用设置连接/读取超时、有限重试和限流处理；重试只在幂等请求上进行。
- 模型输出先做 JSON 结构校验、文件存在性校验、行号范围校验，再入库；校验失败的文件标为跳过或失败，整体按部分完成处理。
- 记录耗时和失败阶段，但日志不打印完整 patch、令牌、密钥或模型原始输入。

### 11.4 缓存与幂等

- PR 预览可以按 `repoFullName + prNumber` 在 Redis 缓存 30–60 秒，减少 GitHub 调用；任务创建必须重新确认 head SHA。
- `Idempotency-Key` 存 Redis，值为请求哈希 + 响应快照，TTL 10 分钟。
- 登录失败计数、JWT 黑名单、游客任务限流都放 Redis。
- 任务状态以数据库为准，Redis 只做短期缓存和限流，不作为唯一状态源。

### 11.5 日志与安全

- 日志字段建议：`traceId`、`userId`、`taskId`、`stage`、`durationMs`、`errorCode`、GitHub 请求状态码。
- 不记录 `guestToken`、JWT、模型密钥、GitHub Token、完整 patch、完整私有代码。
- 游客令牌放在请求头，导出场景的查询参数要避免被访问日志完整记录。
- 错误响应不返回堆栈、SQL、数据库错误信息和第三方原始响应。
- CORS 只允许配置的前端域名；生产环境关闭宽泛的 `*`。
- 接口文档可以和 SpringDoc OpenAPI 保持同步，但本文是接口契约的基准。
